Ignixa · Load Testing

How Locust talks to the Ignixa engine

On each Azure Load Testing engine, the locustfile spawns ignixa-matrix serve as a co-located sidecar and drives it over localhost. The runner — not Locust — carries the FHIR traffic, holds the tokens, and hands back per-operation timings.

Localhost Locust ⇆ runner, ~zero cost
FHIR traffic HTTPS + Bearer, the measured work
Auth & secret client-credentials, cached
Metrics per-op events → ALT dashboard

A Topology — one sidecar per engine

Locust and the runner share the engine instance; the runner embeds the parse-once TestScript engine and owns every hop out to the FHIR server.

B Protocol — start to finish

The runner is parsed once at startup, then evaluated many times. Locust only ever speaks localhost to it; the FHIR round-trips and token handling live entirely inside the runner.

Two hops, very different cost

Locust → runner is a 127.0.0.1 POST — effectively free. The measured latency is the runner → FHIR HTTPS hop, timed at the runner's own HttpClient.

Parse once, run many

Every TestScript is parsed at serve startup into a registry cache; /run evaluates an already-parsed definition, so parsing never taxes the hot path.

Locust never holds a FHIR token

The runner's ClientCredentialsTokenHandler acquires and caches the token (60s expiry buffer, single-flight refresh). Locust only touches auth in the preflight probe.

Per-operation metrics

The engine reports each operation's duration and exchange; the locustfile fires one events.request.fire() per op plus an e2e event, so ALT charts FHIR-operation latency directly.
