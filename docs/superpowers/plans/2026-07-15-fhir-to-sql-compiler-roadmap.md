## Phase 2's framing needs a second correction (verified 2026-07-15, before Phase 2 planning started)

The line above — "model the semantic IR directly against fhir-server's live query-generation code" — turned out to itself be wrong in a specific way, found by actually reading that code structurally before writing Phase 2's plan:

**fhir-server's live code has no typed semantic IR to model against.** `SearchParameterExpression` wraps `SearchParameterInfo` around an inner `Expression`, but that inner expression bottoms out in the same field-level, untyped-value nodes Ignixa already has — `BinaryExpression(BinaryOperator, FieldName, int? ComponentIndex, object Value)` and `StringExpression(StringOperator, FieldName, int? ComponentIndex, string Value, bool IgnoreCase)`. A repo-wide grep for `ISearchValue`/`SearchComparator` under `Features/Search/Expressions/` returns zero hits. Composite component addressing is done via the same `ComponentIndex` int on those field-level nodes — there is no dedicated composite node. Traced the `:exact` string case end to end (`StringOverflowRewriter.VisitString` → `StringQueryGenerator.VisitString`, same worked example the design doc itself used) and it's the same rewrite-then-emit-over-one-untyped-type shape the design doc criticizes in Ignixa — just with more passes (fhir-server's chain is 22 deep).

**Consequence: the typed semantic IR (`SearchParameterPredicateExpression`, typed `ISearchValue`, `SearchComparator`) does not exist anywhere — not in the phantom branch (already ruled out above), and not in fhir-server's actual shipping code either.** It must be designed from scratch, for both repos' eventual benefit, not "modeled against" or ported from an existing richer type. What IS worth reusing from fhir-server, concretely:
- Its **15-node `IExpressionVisitor<TContext,TOutput>` surface** (`VisitSearchParameter`, `VisitBinary`, `VisitChained`, `VisitMissingField`, `VisitMissingSearchParameter`, `VisitNotExpression`, `VisitMultiary`, `VisitUnion`, `VisitString`, `VisitCompartment`, `VisitSmartCompartment`, `VisitInclude`, `VisitSortParameter`, `VisitIn<T>`, `VisitNotReferenced`) as a proven sanity check for how many distinct node kinds a real FHIR search dialect needs — compare Ignixa's own visitor against this count, not against a phantom richer one.
- The **two-stage rewrite-then-emit naming/sequencing pattern** as a structural reference for how *not* to blur stage boundaries (name the type differently at each stage — this is literally the design doc's own "every stage changes type" argument, now independently confirmed against fhir-server's real code rather than assumed).
- **`CompositeComponentExpression`** (from Ignixa's own `worktree-sql-datalayer-architecture` branch) is confirmed to be a **novel Ignixa-side improvement, not a port of anything fhir-server has** — fhir-server has no dedicated composite node at all. Adopt it as planned (see *Relationship to existing work* in the design doc), understanding it as original design work, not fhir-server-derived.
- **The roadmap's "coordinate the `IExpressionVisitor` version bump with fhir-server" framing is misplaced.** `Microsoft.Health.Fhir.Core.csproj` has no `IsPackable`/`PackageId`/version metadata — fhir-server's `Expression`/`IExpressionVisitor` are not a published, versioned surface the way `Ignixa.Search` is. There is no fhir-server-side consumer to break. The only real version-bump coordination needed is **within Ignixa** — between this design's future semantic IR addition and `worktree-sql-datalayer-architecture`'s own in-flight `CompositeComponentExpression` addition to the same visitor interface (both still real, both still need one coordinated major bump — see the Coordination checklist).

**A fifth increment** (`2026-07-16-fhir-to-sql-compiler-composites-remaining.md`, 8 tasks, `worktree-fhir-to-sql-compiler-composites-remaining`) finished the last 4 composite types. Two shared helpers were extracted first (closing the fourth increment's Minor finding and mirroring the earlier `NumericRangeComparison` extraction): `TokenColumnEquality` (the Token-slot logic, now shared by all 6 composite types plus `TokenLoweringRule`'s own precedent) and `DateTimeRangeComparison` (extracted from `DateTimeLoweringRule`, reused by `TokenDateTimeLoweringRule`). Two real design findings, confirmed against source rather than assumed: composite components never carry a `SearchModifier` (`SearchExpressionBinder.BindComposite` always passes `modifier: null` per component), so `TokenStringLoweringRule` only needs the default/`StartsWith` case — the base `StringLoweringRule`'s `:exact`/`:contains` overflow-safety throw guards are unreachable dead weight for a composite's String slot, correctly not reimplemented; and `ReferenceTokenLoweringRule` must resolve its Reference/Token roles by runtime `ISearchValue` type, not array position (some SearchParameter definitions, e.g. `DocumentReference.relationship`, swap which component carries which type — the write path, `RefTokenCompositeRowGenerator.cs`, already handles this the same way, and `CompositeLoweringDispatcher` gets two switch arms for this one type so either component order routes to the same order-agnostic rule). Final whole-branch review: see below.

**A sixth increment** (`2026-07-16-fhir-to-sql-compiler-not-and-resource-columns.md`, 9 tasks + 2 post-final-review fix commits, `worktree-fhir-to-sql-compiler-not-resource-columns`) closed out Phase 5's structural tier: `:not` negation and the three resource-column predicates (`_id`/`_type`/`_lastUpdated`). Two new `CteDefinition` node kinds, `ResourceSource(ResourceTypeId)` (all current, non-deleted resources of a type — deliberately carries no predicate of its own) and `Except(Left, Right)` (a dual-column-correlated `NOT EXISTS` anti-join), give `:not` its shape: `Except(ResourceSource, positiveMatch)`. Resource-column predicates bind through the ordinary search-parameter pipeline (no new expression node — `_id`/`_type` are plain `Token`, `_lastUpdated` is plain `Date`) but are deliberately routed through a new `QueryPlan.OuterPredicate` (an outer `INNER JOIN dbo.Resource` + `WHERE`), not the CTE graph — an explicit, informed user decision made *against* the implementer's own recommendation to use a CTE for reliability against SQL Server's TOP+CTE-inlining predicate-pushdown limitation. `_lastUpdated` duplicates `Ignixa.Domain.Abstractions.IdHelper.ToId()`'s timestamp-encoding formula (millisecond-truncated UTC ticks, left-shifted 3 bits) directly into this Core-tier project, since Core cannot reference that Application-tier project — also user-confirmed — and is scoped to exact-instant values only (`Start == End`); partial-precision ranges throw, deliberately, since no live SQL-generator reference exists yet to verify a range-aware formula against.

**The dominant story of this increment was one recurring bug class, found and fixed four separate times in four different code paths**: a search predicate carrying a `Modifier` (almost always `:not`) silently reaching a lowering path that ignores the modifier and produces a POSITIVE match instead of failing loudly — the exact inverse of what was asked. Occurrences: (1) `Lower.LowerSearchParameter`, single-value `:not` on an ordinary parameter; (2) `ResourceColumnLoweringRule`, single-value `:not` on `_id`/`_type`; (3) `Lower.LowerNode`'s generic leaf dispatch, multi-value `:not` on `_id`/`_type` (this occurrence also disproved the plan's own original claim that the generic dispatcher would "throw" for this shape — it would have silently routed the resource column into `TokenSearchParam`, a real table, just the wrong one); (4) after a dedicated final adversarial re-review found occurrence 3's fix was positional (living in `LowerNode`, one of four real dispatch sites into the leaf/composite rules) rather than structural, the guard was relocated to the two actual choke points, `StructuralContext.Lower`/`LowerComposite`, that every dispatch path funnels through regardless of shape. Each occurrence got an explicit, loud `NotSupportedException` rather than a silent fallback, per this codebase's stated philosophy that a silent wrong answer is worse than a loud failure.

## Open investigation: SQL Server plan-shaping tweaks ("raw SQL" tricks) -- how does a deterministic AST/Emit architecture accommodate them?

**Raised by the user (2026-07-17), not yet investigated -- flagging for a dedicated pass before/during Phase 9 (differential testing against the legacy path is exactly where a real gap would surface).**

fhir-server's hand-written SQL generation makes several low-level, T-SQL-optimizer-specific tweaks that have nothing to do with FHIR search semantics and everything to do with how SQL Server compiles and caches query plans. Two concrete examples the user named:

1. **Embedding catalog values as literals instead of parameters, specifically to shape the cached plan.** SQL Server caches a compiled plan keyed by the query's literal *text* (not its logical shape) when a value is inlined, versus one plan shared across all parameter values when it's parameterized (`sp_executesql`-style) -- the latter risks "parameter sniffing" (a plan optimized for one parameter's cardinality gets reused for a wildly different one, sometimes catastrophically). **This compiler already does exactly this, and it already mattered**: Step 0's own investigation (`docs/features/deployment/investigations/2026-07-15-compartment-search-step0-findings.md`, referenced above) found that literalizing `SearchParamId` (vs. leaving it a captured parameter) closed most of the performance gap to the legacy SQL shape. `ParamSource.SearchParamId` and (after the `:not`/resource-column-predicates and chain increments) `ParamSource.ResourceTypeId`/`ChainJoin`'s catalog ids are all rendered as SQL literals in `Emit`, not `SqlParameterRef`s, deliberately for this reason -- this is a real, working instance of the pattern, not a gap.
2. **Deliberately varying generated SQL text to force a NEW plan compilation ("cache-breaking"), the opposite goal.** Sometimes a cached plan is actively harmful (stale statistics, a pathological parameter-sniffed plan) and the fix is to make SQL Server treat the query as textually distinct so it can't reuse the bad cached entry -- e.g. an injected comment, a varying literal that doesn't affect semantics, or similar. **This is in direct tension with `Emit`'s own load-bearing design invariant, stated in its doc comment since Phase 4**: *"deterministic (same plan -> byte-identical SQL)"* -- which is also what makes every golden-string test in this project's suite meaningful (`Explain()`/`emitted.Sql` assertions assume one plan always produces one exact text). A cache-breaking mechanism, by definition, breaks that determinism for at least some inputs.

**The open question this needs a real investigation pass to answer, not a guess:** does this compiler need a genuine escape hatch for technique 2 (some explicit, narrowly-scoped mechanism -- e.g. an opt-in `QueryPlan` flag that injects a stable-per-invocation-but-varying token, used only when a caller explicitly requests it) or is giving up this specific fhir-server capability an acceptable, even correct, tradeoff given this project's own stated motivation (see `[[fhir-to-sql-compiler-real-motivation]]` memory -- SQL control/maintainability, not chasing every fhir-server perf trick)? Investigate by: (a) finding concrete evidence in fhir-server's real code/issues for when and why it actually uses cache-breaking (is it a real, load-bearing technique with cited incidents, or folklore?); (b) checking whether SQL Server's own `OPTION (RECOMPILE)` hint (a supported, standard mechanism, not a text-varying hack) already solves the same problem more cleanly for whatever fhir-server's hack was working around, in which case `Emit` could support that as a per-plan opt-in without sacrificing determinism at all; (c) deciding, with the user, whether this belongs as part of Phase 9 (differential testing would be the first place a real regression from lacking this shows up) or stays permanently out of scope as a deliberate simplicity tradeoff.
