> **For agentic workers:** This is an INDEX, not an executable plan. Each phase below either links to its own bite-sized plan (written) or is marked "not yet detailed" — do not attempt to execute a phase from this document alone. When a phase's plan doesn't exist yet, write it with `superpowers:writing-plans` when that phase is reached, using this roadmap's dependency and scope notes as input.

**Source design:** `docs/superpowers/specs/2026-07-14-fhir-to-sql-compiler-design.md` ("Ignixa.Search.Sql — Design"). Read that document for full rationale; this roadmap only sequences it and records what's changed since it was written.

**Goal:** Build `Ignixa.Search.Sql`, a pure compiler (Resolve → Lower → Emit) that replaces Ignixa's ad-hoc EF-based FHIR-search-to-SQL translation, on branch `feature/fhir-to-sql-compiler`, gated by an early proof that the approach earns its cost.

## Grounding: what's actually true on this branch right now (verified 2026-07-15)

The design doc is accurate about *current-branch* state everywhere it was checked, but two things it doesn't fully account for changed the picture:

- **Nothing from Phase 1 onward exists yet.** No PR #332 front-end, no semantic IR (`SearchParameterPredicateExpression` doesn't exist — the AST is still field-level `FieldName`/`BinaryExpression`/untyped `object`), no `Ignixa.Search.Sql` project, no `Ignixa.Search.Tests` or `Ignixa.Search.Sql.Tests`. `SearchParameterQueryGenerator.cs` is exactly 2,113 lines as described. `CompartmentSearchProblem.txt` (3,289 lines) exists and matches the design doc's description.
- **A parallel, independent effort — `worktree-sql-datalayer-architecture` (PR #328, open, unmerged) — has already shipped a smaller, incremental refactor of the same subsystem, and goes far less far than this design.** Its own readme (`docs/features/sql-datalayer-architecture/readme.md` on that branch) frames itself as a 4-phase scoped-down alternative to the exact ms-fhir-server "compiler" ambition this design pursues, and explicitly declines to build what this design builds ("Phase 4... deferred, not recommended now... solving a problem the codebase doesn't report having yet"). Status: **Phase 0 (test baseline + mechanical dedup: `ComparisonPredicates`, `TokenCodeStorage`) and Phase 1 (`SearchExpressionQueryBuilder` now implements `IExpressionVisitor` instead of a hand switch) are done in PR #328, open, unmerged.** Phase 2 (a composite semantic leaf — `CompositeComponentExpression` / `IExpressionVisitor.VisitCompositeComponent`, commits `289cd2a9`/`a438048e`) and Phase 3 (data-driven catalog) exist as further commits on that branch beyond PR #328, also unmerged, also not yet a numbered PR.
  - **This branch (`feature/fhir-to-sql-compiler`) currently has NEITHER PR #328 nor its follow-on commits.** `SearchExpressionQueryBuilder.cs:80` here is still a hand-written `expression switch`, not a visitor implementation.
  - **Reuse, don't duplicate.** Per the user's direction: PR #328's dedup and visitor adoption should land (or be merged in) before Phase 1 of this roadmap touches the same files. The composite semantic leaf (`CompositeComponentExpression`) is exactly the node the design doc says this compiler "should adopt... rather than invent a parallel one" (design doc, *Relationship to existing work*) — Phase 5's composite tier-1 rules must be written against that node, not a new one.
  - **Two binary-breaking `IExpressionVisitor` additions are now in flight from two branches** (this design's semantic IR, and whatever `worktree-sql-datalayer-architecture` has already added for composites). The design doc already flags this needs a single coordinated major-version bump, not two. Resolve before Phase 2 of this roadmap, not at the end.
- **The compartment-search "motivating bug" needs re-verification before Step 0 is built as originally scoped.** `src/DataLayer/Ignixa.DataLayer.SqlEntityFramework/Search/CompartmentSearchQueryGenerator.cs` already exists on `main` (introduced in commit `38a979df`, 2025-10-23 — long before `CompartmentSearchProblem.txt` or the design doc) and is the **live production path** for every `CompartmentSearchExpression` (`SearchExpressionQueryBuilder.cs:85`). It already does most of what the design doc's "arm 3/4" (the good shape) describes: one query per unique `SearchParamId`, `UNION`'d together, no `Resource` table join, `resourceTypeIds` forced to inline via `EF.Constant(resourceTypeIds.ToList())` (`CompartmentSearchQueryGenerator.cs:184`) specifically to avoid EF 9's `OPENJSON` parameterization. **The one thing it does NOT do is literalize `SearchParamId` itself** — `refParam.SearchParamId == searchParamId` (`:182`) is still a captured, sniffable parameter. This means the design doc's four-arm factorial, as written, is testing a baseline ("naive EF") that may no longer be reachable in production. Step 0's plan (below) starts with confirming this before building anything.
- **Step 0 result (2026-07-15):** the three-arm timing comparison found literalizing `SearchParamId` closes the gap to the legacy SQL shape (Arm B ≈ Arm C — 950.0ms vs 910.0ms warm, order inverted cold — both meaningfully faster than unmodified Arm A cold (1074-1133ms vs Arm A's 1422ms, ~20-24% faster) but only modestly faster warm (950.0-910.0ms vs Arm A's 1005.7ms, ~6-10% faster)); the original artifact's failure was never a 180s timeout — it's SQL Server Error 8623, a plan-compilation failure thrown after ~7.8s, and `CompartmentSearchQueryGenerator`'s dedup-by-`SearchParamId`/`UNION` shape (which none of the three arms deviate from) already structurally avoids the un-deduplicated, 400+-table-reference query shape that threw it, which is the best-evidenced reason none of the three arms reproduced any failure. Go/no-go is: ship the one-line literalization fix as a standalone PR, and stop treating compartment search as the compiler's headline motivator — full results, caveats, and recommendation in `docs/features/deployment/investigations/2026-07-15-compartment-search-step0-findings.md`.

## Independent items worth their own tickets (not gated on the compiler)

The design doc identifies several live, shipped bugs that are worth fixing regardless of whether this compiler is ever built. None of them block Step 0. Recommend separate bug-fix plans, filed independently:

1. **`TextOverflow` write-convention bug (data-compatibility, silent-wrong-results).** `StringSearchParameterRowGenerator.cs:83-84` writes the *remainder* of a >256-char string to `TextOverflow`; fhir-server writes the *full value*. Confirmed still live on this branch. Needs a migration/reindex, not just a code fix — belongs to `worktree-sql-datalayer-architecture`, and gates Phase 5 above.
2. **Continuation token silent truncation.** An unrecognized/foreign JSON token deserializes to `Offset=0, Count=0` and returns `true` instead of failing closed; the client gets a 200 with a 1-entry bundle and no `next` link. Design doc section *The token format has no owner either — and it is already broken*.
3. **`TokenNumberNumber` composite dispatch gap.** `SearchParameterQueryGenerator.cs:180-198` has no arm for this composite type; falls through to an empty result, silently. Also structurally wrong (passes only 2 of 3 components).
