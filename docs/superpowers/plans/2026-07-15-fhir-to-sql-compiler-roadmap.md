The composite semantic leaf (`CompositeComponentExpression`) is exactly the node the design doc says this compiler "should adopt... rather than invent a parallel one" (design doc, *Relationship to existing work*) — Phase 5's composite tier-1 rules must be written against that node, not a new one.

It already does most of what the design doc's "arm 3/4" (the good shape) describes: one query per unique `SearchParamId`, `UNION`'d together, no `Resource` table join, `resourceTypeIds` forced to inline via `EF.Constant(resourceTypeIds.ToList())` (`CompartmentSearchQueryGenerator.cs:184`) specifically to avoid EF 9's `OPENJSON` parameterization. **The one thing it does NOT do is literalize `SearchParamId` itself** — `refParam.SearchParamId == searchParamId` (`:182`) is still a captured, sniffable parameter. This means the design doc's four-arm factorial, as written, is testing a baseline ("naive EF") that may no longer be reachable in production. Step 0's plan (below) starts with confirming this before building anything.
- **Step 0 result (2026-07-15):** the three-arm timing comparison found literalizing `SearchParamId` closes the gap to the legacy SQL shape (Arm B ≈ Arm C — 950.0ms vs 910.0ms warm, order inverted cold — both meaningfully faster than unmodified Arm A cold (1074-1133ms vs Arm A's 1422ms, ~20-24% faster) but only modestly faster warm (950.0-910.0ms vs Arm A's 1005.7ms, ~6-10% faster)); the original artifact's failure was never a 180s timeout — it's SQL Server Error 8623, a plan-compilation failure thrown after ~7.8s, and `CompartmentSearchQueryGenerator`'s dedup-by-`SearchParamId`/`UNION` shape (which none of the three arms deviate from) already structurally avoids the un-deduplicated, 400+-table-reference query shape that threw it, which is the best-evidenced reason none of the three arms reproduced any failure. Go/no-go is: ship the one-line literalization fix as a standalone PR, and stop treating compartment search as the compiler's headline motivator — full results, caveats, and recommendation in `docs/features/deployment/investigations/2026-07-15-compartment-search-step0-findings.md`.

## Phase 2's framing needs a second correction (verified 2026-07-15, before Phase 2 planning started)

The line above — "model the semantic IR directly against fhir-server's live query-generation code" — turned out to itself be wrong in a specific way, found by actually reading that code structurally before writing Phase 2's plan:

**fhir-server's live code has no typed semantic IR to model against.** `SearchParameterExpression` wraps `SearchParameterInfo` around an inner `Expression`, but that inner expression bottoms out in the same field-level, untyped-value nodes Ignixa already has — `BinaryExpression(BinaryOperator, FieldName, int? ComponentIndex, object Value)` and `StringExpression(StringOperator, FieldName, int? ComponentIndex, string Value, bool IgnoreCase)`. A repo-wide grep for `ISearchValue`/`SearchComparator` under `Features/Search/Expressions/` returns zero hits. Composite component addressing is done via the same `ComponentIndex` int on those field-level nodes — there is no dedicated composite node. Traced the `:exact` string case end to end (`StringOverflowRewriter.VisitString` → `StringQueryGenerator.VisitString`, same worked example the design doc itself used) and it's the same rewrite-then-emit-over-one-untyped-type shape the design doc criticizes in Ignixa — just with more passes (fhir-server's chain is 22 deep).

**Consequence: the typed semantic IR (`SearchParameterPredicateExpression`, typed `ISearchValue`, `SearchComparator`) does not exist anywhere — not in the phantom branch (already ruled out above), and not in fhir-server's actual shipping code either.** It must be designed from scratch, for both repos' eventual benefit, not "modeled against" or ported from an existing richer type. What IS worth reusing from fhir-server, concretely:
- Its **15-node `IExpressionVisitor<TContext,TOutput>` surface** (`VisitSearchParameter`, `VisitBinary`, `VisitChained`, `VisitMissingField`, `VisitMissingSearchParameter`, `VisitNotExpression`, `VisitMultiary`, `VisitUnion`, `VisitString`, `VisitCompartment`, `VisitSmartCompartment`, `VisitInclude`, `VisitSortParameter`, `VisitIn<T>`, `VisitNotReferenced`) as a proven sanity check for how many distinct node kinds a real FHIR search dialect needs — compare Ignixa's own visitor against this count, not against a phantom richer one.
- The **two-stage rewrite-then-emit naming/sequencing pattern** as a structural reference for how *not* to blur stage boundaries (name the type differently at each stage — this is literally the design doc's own "every stage changes type" argument, now independently confirmed against fhir-server's real code rather than assumed).
- **`CompositeComponentExpression`** (from Ignixa's own `worktree-sql-datalayer-architecture` branch) is confirmed to be a **novel Ignixa-side improvement, not a port of anything fhir-server has** — fhir-server has no dedicated composite node at all. Adopt it as planned (see *Relationship to existing work* in the design doc), understanding it as original design work, not fhir-server-derived.
- **The roadmap's "coordinate the `IExpressionVisitor` version bump with fhir-server" framing is misplaced.** `Microsoft.Health.Fhir.Core.csproj` has no `IsPackable`/`PackageId`/version metadata — fhir-server's `Expression`/`IExpressionVisitor` are not a published, versioned surface the way `Ignixa.Search` is. There is no fhir-server-side consumer to break. The only real version-bump coordination needed is **within Ignixa** — between this design's future semantic IR addition and `worktree-sql-datalayer-architecture`'s own in-flight `CompositeComponentExpression` addition to the same visitor interface (both still real, both still need one coordinated major bump — see the Coordination checklist).

## Independent items worth their own tickets (not gated on the compiler)

The design doc identifies several live, shipped bugs that are worth fixing regardless of whether this compiler is ever built. None of them block Step 0. Recommend separate bug-fix plans, filed independently:

1. **`TextOverflow` write-convention bug (data-compatibility, silent-wrong-results) — code fixed, reindex/backfill still outstanding.** `StringSearchParameterRowGenerator.cs` wrote the *remainder* of a >256-char string to `TextOverflow` instead of the *full value* fhir-server writes. **Fixed** as task 1 of `2026-07-15-fhir-to-sql-compiler-phase4-5-ast-emit-lower.md` (write path + all four read-path reconstruction call sites in `SearchParameterQueryGenerator.cs`), narrowed to `StringSearchParam` only — `TokenStringCompositeRowGenerator.cs`/`RefTokenCompositeRowGenerator.cs` still carry the identical defect for their own overflow columns, deferred to whichever phase implements those composite leaf rules. **No reindex/backfill mechanism exists anywhere in this codebase** (`BackgroundJobType.Reindex` is an unused stub) — confirmed during that same task. **Do not deploy the fixed write path against any database holding pre-existing >256-char string search values until a backfill tool is built and run**; this is a separate, substantial follow-up, not covered by the fix above.
2. **Continuation token silent truncation.** An unrecognized/foreign JSON token deserializes to `Offset=0, Count=0` and returns `true` instead of failing closed; the client gets a 200 with a 1-entry bundle and no `next` link. Design doc section *The token format has no owner either — and it is already broken*.
3. **`TokenNumberNumber` composite dispatch gap.** `SearchParameterQueryGenerator.cs:180-198` has no arm for this composite type; falls through to an empty result, silently. Also structurally wrong (passes only 2 of 3 components).
