# Ignixa.DataLayer.SqlServer: Design

**Builds on:** `feature/fhir-to-sql-compiler` at the point Phase 9 (compiler completeness — `_summary=count`/`_total=accurate`, `:missing`) merged (commit `659c971a`). `Ignixa.Search.Sql` (the FHIR-to-SQL compiler) is architecturally complete for leaf types, composites, chain, includes, compartment search, sort, and count, but not yet at full feature parity with the legacy engine (see §7).

**Scope of this document:** the architecture for a new project, `Ignixa.DataLayer.SqlServer`, that will eventually fully replace `Ignixa.DataLayer.SqlEntityFramework` — writes, reads, and schema/migration management — built on raw ADO.NET (no EF Core, no ORM), SQL Database Projects for schema, and a new per-tenant schema-version compatibility mechanism for rolling upgrades. This document covers architecture and phasing, not a task-by-task implementation plan for every phase — each phase gets its own plan later, matching how `docs/superpowers/plans/2026-07-15-fhir-to-sql-compiler-roadmap.md` itself works.

---

## 1. Ground truth (research findings, not assumptions)

Three parallel investigations grounded this design before any architecture was proposed:

**"The old project" the user referenced (multi-schema/instance roll-forward) is real Microsoft fhir-server, not a prior Ignixa project.** Checked exhaustively across ~90 branches in ignixa-fhir's git history — no DataLayer project with schema-version rolling-upgrade support, and no schema-per-tenant model, ever existed in this repo. Ignixa's multi-tenancy has always been connection-string-per-tenant (`TenantConfiguration.Storage.ConnectionString`, confirmed in `src/Application/Ignixa.Domain/Models/TenantConfiguration.cs:104`) — **database-per-tenant**, not schema-per-tenant or a shared database with a tenant column.

**fhir-server's real connection/execution layer is `ISqlRetryService`** (not `SqlConnectionWrapperFactory`/`SqlCommandWrapper` — that naming is stale, from an older fhir-server version). Confirmed in the local checkout (`src/Microsoft.Health.Fhir.SqlServer/Features/Storage/SqlRetry/`): direct `Microsoft.Data.SqlClient` types, a retry policy, an `isReadOnly` flag for read-replica routing, structured event logging. Both `SqlServerSearchService` (reads) and `SqlServerFhirDataStore` (writes/merge) inject and use the *same* instance — one unified connection layer, no ORM anywhere, no split between read and write paths.

**fhir-server's schema-version rolling-upgrade compatibility is real, load-bearing production infrastructure** — one constant in `SchemaVersionConstants.cs` is commented "currently used in Azure Healthcare APIs." The app declares an 11-version compatibility window (`Min = V103, Max = V113` in the checked-out commit) plus ~30 named per-feature version-gate constants, each checked at runtime via `IsEnabled(sqlRetryService)`-style calls throughout the write path. **The generic engine underneath (`SchemaInformation`, the actual upgrade runner, any `/_schema` endpoint) lives in a separate, external NuGet package** (`Microsoft.Health.SqlServer`, from the `healthcare-shared-components` repo, not `microsoft/fhir-server`) that ships compiled, not as source — it could not be inspected. Only the *consumption* pattern (constants + runtime checks) is visible and portable; the actual upgrade-runner mechanism is not something that can be ported, only reimplemented from scratch, informed by the pattern.

**fhir-server does have a real, per-object-type declarative schema source** (`src/Microsoft.Health.Fhir.SqlServer/Features/Schema/Sql/{Tables,Views,Sprocs,Types,Scripts}/`, e.g. `Tables/Resource.sql`, `Tables/DateTimeSearchParam.sql`) — but it is not wrapped in a formal `.sqlproj`/SSDT project, and no generator script that produces the numbered migration files from it is visible in this checkout. The numbered migration scripts themselves (`Migrations/90.sql` through `113.sql`, each with a paired `.diff.sql`) carry an "Auto-Generated from Sql build task. Do not manually edit it" header — the exact same boilerplate Ignixa's own `97.sql` baseline inherited verbatim when it was copied from fhir-server. This confirms SSDT-style generation exists somewhere in Microsoft's internal tooling, but it is not accessible to copy — "leverage database projects like fhir-server" means building an Ignixa-original SSDT adoption using the *visible* per-object-file organization as a template, not porting real generator code.

**fhir-server's real latest schema version is V113** (confirmed directly against the checkout: `SchemaVersion.cs`'s enum tops out at `V113`, and `Migrations/113.sql`/`113.diff.sql` exist). Ignixa's `97.sql` baseline is 16 versions behind. **But every one of those 16 versions (98 through 113) is pure stored-procedure churn** — `ALTER PROCEDURE`/`DROP PROCEDURE` for `MergeResources`, `MergeSearchParams`, job-queue procedures, search-optimization procedures. A direct grep of all 16 diff scripts for `CREATE|ALTER|DROP TABLE|INDEX|COLUMN` returns **zero matches**. Ignixa's table schema is very likely already structurally equivalent to fhir-server's v113 tables — there is no table-schema catch-up gap to close, only a stored-procedure history Ignixa doesn't consume (it never adopted fhir-server's actual stored procedures — `SqlMergeRepository`/`RowGenerators` are Ignixa-original write-path code) but which may still be worth reading for bug-fix/optimization lessons (§7, out of scope for this document).

**SQL Database Projects (SDK-style `.sqlproj`, `Microsoft.Build.Sql`) are independently confirmed feasible in this repo's actual toolchain.** `global.json` targets .NET SDK 10.0.100 (well above `Microsoft.Build.Sql`'s requirement); CI (`.github/workflows/pr-build.yml`) already runs on `ubuntu-latest` with a live SQL Server container for E2E tests; `Microsoft.Build.Sql`-based projects build cross-platform via plain `dotnet build` (unlike the legacy Windows/VS-only SSDT MSBuild targets); zero existing SSDT references anywhere in the repo — this is new adoption, not extending something partial. The official CLI workflow (confirmed against the live Microsoft Learn documentation, not from memory): `dotnet tool install -g Microsoft.SqlPackage` + `dotnet new install Microsoft.Build.Sql.Templates` → `dotnet new sqlproj -n <name>` → one `.sql` file per object → `dotnet build` produces a `.dacpac` → `sqlpackage /Action:Publish` or `/Action:DeployReport` deploys/previews against a target. **Deployment is diff-based and idempotent**: `sqlpackage` compares the `.dacpac`'s declared state against whatever's actually in the target database and generates the necessary `CREATE`/`ALTER` statements on the spot — a fundamentally different mechanism from both Ignixa's current EF Migrations and fhir-server's own numbered scripts, neither of which trusts an auto-generated diff. `sqlpackage` itself has no concept of "the app needs schema version N through N+1 simultaneously" — that capability does not come from the tooling; it is Ignixa's own layer (§4) on top.

**A genuine architectural mismatch with fhir-server, not papered over**: fhir-server's SQL layer has zero multi-tenancy inside it — it's single-database-per-deployment; multi-tenancy where it exists in fhir-server sits in a separate, thin (9-file), essentially unreferenced project above the data store. fhir-server never had to solve "which tenant's database is on which schema version, with old and new app code running concurrently during a rolling deployment." This is why §4 is original design, not a port.

## 2. Scope decision: full replacement

`Ignixa.DataLayer.SqlServer` is designed to **fully replace** `Ignixa.DataLayer.SqlEntityFramework` — writes (`SqlMergeRepository`'s TVP-based bulk merge), reads (`SqlEntityFrameworkSearchService`'s 1,329-line LINQ engine, replaced by compiled search), and schema/migration management (EF Core Migrations, replaced by SQL Database Projects) — not a narrower "new project for compiled-search reads only, EF keeps writes" scope. This is a larger, riskier undertaking than the narrower scope would have been (it touches production write paths that work today), a deliberate choice, not a default.

**The read-path cutover is gated on `Ignixa.Search.Sql` reaching full feature parity with the legacy engine** — known gaps as of this document: `:ap` comparator, Quantity System/Code matching, `_lastUpdated` partial-precision ranges, Reference `:identifier`/type modifiers, true multi-level `:iterate`. No fallback dispatch (compiled-path-where-supported, legacy-path-for-the-rest) is planned — closing every gap is a prerequisite for cutover, not a permanent split. This means Phase E (§3) cannot start until those compiler gaps close, in separate future phases of the compiler roadmap, not this document.

## 3. Phased roadmap

Six phases, each independently plannable and reviewable, matching the discipline used throughout the `fhir-to-sql-compiler` roadmap (isolated worktree, subagent-driven execution, task-scoped review, final whole-branch review before merge):

- **Phase A — Project skeleton + connection/execution layer.** New `Ignixa.DataLayer.SqlServer` project; `ISqlExecutionService` (§4), no schema-version awareness yet. Zero production-facing change — nothing else depends on this project existing yet.
- **Phase B — SQL Database Projects adoption.** New SDK-style `.sqlproj`; full decomposition of `97.sql` into per-object files now (§5), verified via a zero-diff `DeployReport` check, not incremental adoption. `SqlCatalogGenerator` gains a new input source. CI gains a `dotnet build` → `.dacpac` → `sqlpackage /Action:DeployReport` step producing a reviewable artifact; `/Action:Publish` never runs unattended (§5).
- **Phase C — Schema-version compatibility layer.** Per-tenant `SchemaVersion` tracking, the app's compiled-in compatibility window, version-gated behavior, expand/contract migration discipline (§6).
- **Phase D — Write-path migration.** Port `SqlMergeRepository`'s TVP-based bulk writes from EF's `Database.ExecuteSqlRawAsync` to `ISqlExecutionService` directly. Lower risk than it sounds — the write path is already raw SQL text execution, not LINQ; this swaps the connection/execution wrapper underneath, not the write logic itself.
- **Phase E — Read cutover.** Gated on `Ignixa.Search.Sql` reaching full parity (§2). Wires compiled search into `ISqlExecutionService`, retires `SqlEntityFrameworkSearchService`.
- **Phase F — Retire `Ignixa.DataLayer.SqlEntityFramework`** once A–E are all live and verified.

## 4. Connection/execution layer

`ISqlExecutionService` (naming placeholder, to be finalized at implementation time), mirroring `ISqlRetryService`'s real shape (§1), unified for reads and writes from Phase A:

- **Connection management**: standard ADO.NET pooling per connection string. Since each tenant already has its own connection string (§1), pooling is naturally per-tenant — no new pooling logic beyond what `Microsoft.Data.SqlClient` already provides.
- **Retry policy**: transient-fault handling (deadlocks, timeouts, connection resets) — standard, not novel design work.
- **Execution helpers**: thin wrappers around raw `SqlCommand` (`ExecuteReaderAsync`, `ExecuteNonQueryAsync`, etc.). `Ignixa.Search.Sql`'s `EmittedSql` (a SQL string plus an ordered parameter list) binds directly into a `SqlCommand` via these helpers — this is the seam that makes the compiler's raw-T-SQL output a natural fit for this layer, in a way it never was for EF's LINQ-based query building.
- **The Phase C hook**: every call is tagged with the target tenant's current schema version (looked up/cached per-tenant, §6), which version-gated code paths consult.
- **No read-replica routing** (fhir-server's `isReadOnly` flag). No evidence Ignixa has read-replica infrastructure today; deferred until there's a real replica to route to (§7).

**Symbol resolution**: `Ignixa.DataLayer.SqlEntityFramework.Search.SqlEntityFrameworkSymbolResolver` (bridges into `Ignixa.Search.Sql`'s `ISymbolResolver` by wrapping an EF-coupled `SearchIndexReferenceDataCache`) needs a direct raw-ADO.NET equivalent in the new project — same caching semantics, querying through `ISqlExecutionService` instead of a `DbContext`. Mechanical, not a design risk.

## 5. Schema management (SQL Database Projects)

**Decomposition**: build a new SDK-style `.sqlproj` (`Microsoft.Build.Sql`) by splitting `97.sql`'s `CREATE TABLE`/`CREATE INDEX`/`CREATE PARTITION FUNCTION`/etc. statements into per-object files, organized using fhir-server's real `Tables/Views/Sprocs/Types/Scripts` folder structure (§1) as the template — not inventing a new organization scheme.

**Verification, not inspection**: build a database from `97.sql` directly (the existing `DatabaseInitializer` bootstrap path, unchanged), build the new `.sqlproj` to a `.dacpac`, run `sqlpackage /Action:DeployReport` comparing the dacpac against that database, and require **zero diff** before treating the decomposition as correct. This is the same zero-diff discipline this project has used for every prior structural change this session (e.g. the Phase 8 part 1 compartment CTE reorg, the Checkpoint 1.5 `Lowering/` folder split) — a mechanical proof, not a manual review claim.

**`SqlCatalogGenerator`'s new input**: currently reads `97.sql` via `AdditionalFiles` matched by filename (`src/Core/Ignixa.Search.Sql.Generators/SqlCatalogGenerator.cs`). Once the decomposition is verified zero-diff, the generator switches to reading the SSDT project's per-object files directly — a one-time input-source swap, not a redesign of what it extracts (table/column facts).

**Deploy flow — always generate-then-review, never auto-publish.** CI (and any real deploy pipeline) runs `sqlpackage /Action:DeployReport` (or `/Action:Script`) to produce a reviewable diff artifact; `/Action:Publish` never runs unattended against any real database. This matches how every schema change in this project has always gone through explicit, human-reviewed SQL in a PR — `sqlpackage`'s diff-based publish is powerful but capable of generating destructive statements (a `DROP COLUMN` an author didn't intend) without careful review, which is unacceptable for a production healthcare system.

**EF Core Migrations retire as the schema-authoring mechanism** once the decomposition lands — the 6 existing EF migrations (background jobs, package/terminology indexes, terminology import tracking, resource TTL, source events, search-param extension columns) fold into the SSDT baseline as part of decomposition. `Ignixa.DataLayer.SqlEntityFramework`'s `DbContext` still needs *some* way to know the current schema shape for its own query mapping until Phase F retires it entirely — this is a Phase B/D boundary detail not fully resolved by this document; the implementation plan for Phase B must address it explicitly, not leave it implicit.

## 6. Schema-version compatibility layer

**Storage**: a `SchemaVersion` table *inside each tenant's own database* — not a shared/global table, since there is no shared database (§1). Tracks that database's currently-applied version. Mirrors fhir-server's per-database "current version" row, scoped per-tenant since Ignixa has N independent databases instead of fhir-server's one.

**Compatibility window**: the *app build* (not the database) declares a compiled-in `MinimumSupportedSchemaVersion`/`MaximumSupportedSchemaVersion` pair, mirroring `SchemaVersionConstants.Min`/`.Max` (§1). Global to the running code, identical across every tenant a given instance serves.

**Per-tenant version check**: when the connection layer opens (or refreshes a cached connection to) a tenant's database, it reads that tenant's `SchemaVersion` row and checks it against the app's window. Below the app's minimum → that tenant hasn't been upgraded yet. Above the app's maximum → an old app instance talking to an already-upgraded tenant, mid-rolling-deploy. Both are expected, routine states during a rollout, not error conditions.

**Version-gated behavior**: mirroring fhir-server's ~30 named per-feature version-gate constants + runtime checks (§1) — any code path whose SQL depends on a specific schema shape checks "is *this tenant's* current version at-or-above the version this shape requires" before using it, falling back to older-compatible behavior otherwise. Same mechanical pattern as fhir-server, keyed per-tenant instead of once globally at startup.

**What actually makes this safe is expand/contract discipline, not the tracking table.** The table is bookkeeping. Every schema change ships in two steps: *expand* — purely additive (new nullable columns, new tables, never a destructive rename/drop) — deployed and proven working against *old* app code first; *contract* — removing what's no longer needed — only once every app instance is confirmed running code that no longer depends on the old shape. This is exactly where §5's deploy-report-then-review step earns its keep: a destructive statement appearing in a `DeployReport` diff during what should be an additive-only change is precisely what a human reviewer must catch.

**Why this is not portable from fhir-server as a mechanism, only as a pattern** (§1): fhir-server solves a *temporal* problem (one shared database, old and new code both hitting it during a single migration window). Ignixa's problem is *spatial* — many independent tenant databases, each upgradeable on its own schedule — with the classic temporal window still present, but scoped to *each tenant's own* upgrade moment rather than the whole fleet simultaneously.

## 7. Explicitly out of scope

Named here so it is not silently assumed or silently dropped later:

- **Read-replica routing** — deferred until there's real replica infrastructure to route to (§4).
- **Reviewing fhir-server's v98–v113 stored-procedure history for bug fixes/optimizations** — a real, separate research task the user asked for, not schema or architecture work. Tracked as a follow-up, not performed by this document.
- **The compiler-parity gaps themselves** (`:ap`, Quantity System/Code matching, `_lastUpdated` partial-precision ranges, Reference `:identifier`/type modifiers, multi-level `:iterate`) — `Ignixa.Search.Sql` work, tracked in the compiler's own roadmap, a prerequisite for Phase E but not built by this document.
- **Task-by-task implementation plans for Phases A–F** — this document is architecture and phasing; each phase gets its own `writing-plans`-produced plan when its turn comes, matching the compiler roadmap's own pattern.
- **The `Ignixa.DataLayer.SqlEntityFramework` `DbContext`'s schema-shape awareness during the Phase B/D transition window** — flagged in §5 as a real, unresolved boundary detail for Phase B's own implementation plan to address explicitly.

## 8. Testing

Differential testing is the central discipline, not incidental coverage — this project's own retrospective (recorded in the compiler roadmap) has repeatedly found that "composes correctly by construction" claims need empirical proof, not just structural trace. Concretely:

- **Golden-shape tests** for `ISqlExecutionService` and every new component — exact assertions, never loose non-null checks, matching every prior increment's discipline this session.
- **A genuine differential-test suite** comparing `Ignixa.DataLayer.SqlServer`'s behavior against `Ignixa.DataLayer.SqlEntityFramework`'s current behavior — for reads once compiler parity is reached (Phase E), for writes once Phase D ports the write path. Already flagged as needed in the Phase 9 roadmap write-up for exactly this reason (the compartment `ReferenceResourceTypeId` gap, the `_include` `SearchParamId` filtering gap, and the composite `:missing` legacy divergence were all found by comparing against real legacy behavior, not by inspection alone).
- **§5's zero-diff `DeployReport` check** is itself a differential test applied to schema, not just a one-time decomposition proof — it should remain a standing CI check, not a single verification run.
