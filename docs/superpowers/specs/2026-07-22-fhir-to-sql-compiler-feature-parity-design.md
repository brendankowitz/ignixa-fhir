# Sub-project 1: Compiler Feature-Parity — Design

**Branch:** `worktree-ignixa-datalayer-sqlserver` (worktree `.claude/worktrees/ignixa-datalayer-sqlserver`). No new branch. Touches `Ignixa.Search.Sql` / `Ignixa.Search.Sql.Generators` only — no `Ignixa.DataLayer.SqlServer` or `Ignixa.DataLayer.SqlEntityFramework` changes here.

## Context

This is sub-project 1 of 3 replacing the original, too-large "Phase E" design (`docs/superpowers/specs/2026-07-22-datalayer-sqlserver-phase-e-search-adapter-design.md` — superseded, do not plan from it). A Fable review of that design found the proposed `SqlServerCompiledSearchService` adapter's execution model unworkable, and separately confirmed real feature gaps that a no-flag hard cutover would turn into live regressions. This sub-project closes those gaps at the compiler level, before any adapter work begins (sub-project 3).

**Not in scope here** (confirmed separately): the `ct`→`cancellationToken` rename, the `SearchCompartmentHandler` nested-`And` bug, the `SqlServerRepositoryFactory` composition-root move, and the `SqlServerFhirRepository.cs` cleanup are sub-project 2. The adapter itself, the corrected `Resolve`→`Lower`→`SqlBuilder` execution model, the differential harness, and the cutover are sub-project 3.

**Unrelated, non-overlapping work in flight**: `origin/brendankowitz-implement-sql-search-gaps` (unfinished, no PR) is a separate track closing predicate/leaf-value gaps (system-qualified token/quantity matching, URI `:above`/`:below`, external reference identity, string overflow) — explicitly scoped as "wiring into production remains out of scope" in its own design doc. Zero file/scope overlap with this sub-project; proceeds independently.

## Scope

1. Token/Number/Quantity/Reference/Uri sort-parameter-type support (`_sort`).
2. The 3-sort-key cap: **stays at 3** (explicit user decision — not raised, not removed, despite legacy having none).
3. A new, purpose-built continuation-token format for keyset paging — no legacy-token compatibility (explicit user decision: a hard cutover means in-flight legacy tokens simply go stale; client restarts from page 1).
4. System-level (cross-resource-type) search.
5. `$everything` (`GET /[type]/[id]/$everything`).

## 1. Generalized sort-type support

**Finding**: legacy's Token/Number/Quantity/Reference/Uri sort (`SqlEntityFrameworkSearchService.cs:776-854`) is one mechanism repeated five times — `LEFT JOIN` to the type's search-index table (filtered by `ResourceSurrogateId` + `SearchParamId`) → project one column → `MIN()`/`MAX()` per ASC/DESC. Only the table+column differ (`TokenSearchParam.Code`, `NumberSearchParam.LowValue`, `QuantitySearchParam.LowValue`, `ReferenceSearchParam.ReferenceResourceId`, `UriSearchParam.Uri`). Quantity needs no System/unit-normalization special-casing — plain `LowValue`, identical shape to Number.

**Design**: add one new `SortKeyKind` member (not five) — call it `SortKeyKind.Aggregated` — carrying a table+column reference resolved via `SqlCatalog` (the same catalog-driven table/column resolution leaf lowering already uses per `SearchParamType`), plus the ASC/DESC-driven `MIN`/`MAX` choice. `String`/`Date`/`_lastUpdated` keep their existing `SortKeyKind` members and `IsMin`/`IsMax`-flagged-row join (a write-path optimization avoiding aggregation entirely) — **do not** force the five new types onto that mechanism. Confirmed by direct inspection of `src/DataLayer/Ignixa.DataLayer.SqlServer.Database/Tables/`: `IsMin`/`IsMax` exist only on `StringSearchParam.sql` and `DateTimeSearchParam.sql` — Token/Number/Quantity/Reference/Uri tables definitively lack them. `Aggregated` is the only sound mechanism for these five types; this is settled, not a plan-time open item.

Boundary-value typing for Section 3's continuation token: once `Aggregated` collapses five leaf types into one `SortKeyKind`, the kind alone no longer determines the boundary value's CLR type (Token→string, Number/Quantity→decimal, etc.). Resolve via the carried `ColumnDescriptor.SqlType` on the `SortKey`, not the `SortKeyKind` — the adapter (sub-project 3) parses each boundary value using that type, not a kind-keyed switch.

`BuildSortKey` (`Lower.cs:376-384`) gains one new dispatch arm instead of five. `SortKey` itself needs new fields to carry `Aggregated`'s table+column (today it's just `(short? SearchParamId, SortKeyKind Kind, SortOrder Direction)` — no table/column at all, since `String`/`Date` currently hard-code their table name inline in `SqlBuilder.cs` rather than carrying it on `SortKey`). `Emit`'s three sort-emission methods (`EmitSortJoins`, `EmitMissingPrimaryFilter`, `SortValueExpr`) each need a genuinely new third branch, not an extension of their existing `String`-vs-`Date` ternary: `Aggregated` cannot reuse the `IsMin`/`IsMax`-flagged-row `JOIN` shape (those columns don't exist on the five new tables) — it needs a `LEFT JOIN` to a derived table doing `MIN`/`MAX` aggregation grouped by `ResourceSurrogateId`, e.g. `LEFT JOIN (SELECT ResourceSurrogateId, MIN(Code) AS AggValue FROM dbo.TokenSearchParam WHERE ResourceTypeId = m.T1 AND SearchParamId = 202 GROUP BY ResourceSurrogateId) sk0 ON sk0.ResourceSurrogateId = m.Sid1`. The `ISNULL(..., sentinel)` wrapping and `NOT EXISTS`-based `MissingPrimary` filter generalize cleanly once the table/column come from `SortKey`'s new fields instead of a hard-coded ternary — only the join shape itself is new machinery.

Stays at 3. No code change beyond whatever the new sort-type support naturally requires at the existing cap boundary.

## 3. Continuation-token format

**Finding**: the compiler's `PageSpec` (`SortSpec.cs:49-52`) is a keyset boundary — `IReadOnlyList<SqlParameterRef> Boundary` (one value per active sort key, already sentinel-substituted per `Emit`'s NULL-handling rules) + `BoundaryResourceTypeId` + `BoundarySurrogateId`. This is structurally incompatible with legacy's offset+count token (`ContinuationToken.cs:22-71`) — not a format difference to bridge, a different pagination model entirely (keyset vs. offset).

**Design**: a new type (e.g. `KeysetContinuationToken`) encoding `{BoundaryValues: string[], BoundaryResourceTypeId: int, BoundarySurrogateId: long}` as base64 JSON, matching legacy's *encoding style* (base64-wrapped JSON) but a wholly different payload shape. `Encode`/`TryDecode` static methods mirroring `ContinuationToken`'s existing shape for familiarity. `BoundaryValues` are stored as strings (not typed) since the boundary values' actual CLR types vary per sort key (string/date/numeric/etc.) and round-tripping through a single serialization-friendly representation is simpler than a discriminated payload — the adapter (sub-project 3) is responsible for parsing each value back to the right type using the corresponding `SortKey`'s `ColumnDescriptor.SqlType` (per Section 1 — not a `SortKeyKind`-keyed switch, since `Aggregated` alone doesn't determine the CLR type) when constructing a `PageSpec`. This type lives in `Ignixa.Search.Sql` (not `Ignixa.Search`, where the legacy token lives) since it's coupled to `PageSpec`'s shape, not to `SearchOptions`.

## 4. System-level search

**Finding**: `resourceType` is a required, non-nullable parameter threaded through the entire `Lower` dispatch tree (`Lower.cs:96-98` and every leaf/composite/`And`/chain dispatch site), and `ParamSource.ResourceTypeId` renders as a SQL literal per lowering pass (the established plan-shaping technique this compiler uses throughout). The existing wildcard-compartment mechanism (`Lower.cs:52` → `Lowering/StructuralContext.cs:223-251` — corrected path; not `Symbols/StructuralContext.cs`) is not reusable: it resolves compartment *membership* itself across a bounded, known type set and never calls `RequireResourceType`-guarded dispatch at all, whereas system-level search needs the *same arbitrary expression tree* evaluated with no type constraint.

**Cross-check against `microsoft/fhir-server`'s real SqlServer engine** (not just Ignixa's EF port): its per-type predicate generators (`SearchParamTableExpressionQueryGenerator`-derived, one per `SearchParamType`) carry **no `ResourceTypeId` at all** — every predicate CTE is inherently type-agnostic. Type constraints apply as a **separate rewrite pass** (`TypeConstraintVisitor`), layered on top of predicate logic rather than baked into each predicate node. This is architecturally cleaner than a single node type toggling between "typed" and "type-less" modes, and is the model this section now follows for **system-level search specifically** — ordinary typed search's existing `ParamSource`/`ResourceSource` literal-`ResourceTypeId` embedding, covering Phases 1-9's entire proven, tested surface, is **unchanged**. This is not a codebase-wide unification (that would touch hundreds of existing passing tests and sacrifice the literal-ID plan-shaping optimization that benefits the overwhelming majority of ordinary, typed queries) — it is a type-constraint mechanism scoped to the one new capability that genuinely needs it.

**Design, revised after two review rounds**: the original proposal (run `LowerNode` once per candidate resource type, `Union` the results) had a real scaling problem — unioning across the full ~140+ resource-type catalog with no `_type` filter risks the exact SQL-plan-compilation failure (SQL Server error 8623 at ~422 ungrouped table references) that compartment search's own grouped-by-`SearchParamId` redesign exists specifically to avoid. Legacy sidesteps this: it compiles system search as a **single untyped query** (`SqlEntityFrameworkSearchService.cs:320-324` passes a `null` resource-type-id).

`ParamSource`/`ResourceSource` gain a **nullable** `ResourceTypeId` (`short?`, down from `short`) — when null, `Emit` omits the `ResourceTypeId` filter entirely from that CTE's `WHERE` clause, matching one CTE per search parameter across every resource type that has a row for it (mirrors compartment search's group-by-`SearchParamId` anti-explosion strategy; matches legacy's single-query approach). Correction from the prior draft: `ResourceSource.ResourceTypeId` already renders as a **bound parameter** today (`EmitResourceSource`, `SqlBuilder.cs:505-511` — `WHERE ResourceTypeId = @pN`), not a literal like `ParamSource`'s — so nullability there costs no existing plan-shaping optimization at all; only `ParamSource`'s literal rendering (ordinary typed search, unaffected by this change) has that property to begin with.

**Type-constraint composition reuses existing machinery, not a new outer-filter construct.** `_type=X` (single value) already lowers to a resource-column predicate via `ResourceColumnLoweringRule.TypeEquals` → `Predicate.Equal(ResourceTypeId, ...)`, flowing through the **existing** `QueryPlan.OuterPredicate` → `INNER JOIN dbo.Resource` mechanism (`SqlBuilder.cs:40-48, 63-95`) — this is already, structurally, this compiler's own version of a separate type-constraint pass, applied uniformly regardless of how the match set was assembled. The genuinely new gap is `_type` with a **comma-separated list** (`GET /?_type=Patient,Observation`): `TypeEquals` today only produces `Predicate.Equal` (single value), and `ExtractResourceColumnPredicates` (`Lower.cs:202-231`) only pulls resource-column predicates out from beneath a top-level `And`, not an `Or` of several `TypeEquals` — whether comma-separated `_type` already works via some other path, or is a distinct, pre-existing gap unrelated to system-level search, is **unverified and must be confirmed at task time before writing code**, not assumed. If it's a real gap, close it by extending `TypeEquals` to accept a value list (`Predicate.In`, if that variant exists, or an `Or` of `Equal`s recognized by `ExtractResourceColumnPredicates`) — this closes the gap for **typed** search too (a real `_type=Patient,Observation` bonus fix), not just system-level search.

**Resource-column predicates and the base case.** `_id`/`_type`/`_lastUpdated` route through `OuterPredicate`, not `ParamSource` — already type-agnostic by construction (`EmitPredicate`'s `OuterPredicate` rendering doesn't reference `ResourceTypeId`). The base case (bare `GET /`, or `GET /?_lastUpdated=gt...` with nothing else) comes from `ResourceSource`/`LowerResourceSource`, which needs the same nullable-`ResourceTypeId` treatment as `ParamSource` for exactly this shape — legacy's own untyped base query (`SqlEntityFrameworkSearchService.cs:312-315`) and the most common system-level query in practice.

**Composition limits, explicit and deliberate** (matching this project's established "throw loudly, document the gap" pattern): initial scope covers ordinary leaf/composite/`And`/`Or` predicates (type-less `ParamSource`) and resource-column/base predicates (type-less `ResourceSource`). Chain, `:not` (which internally calls `LowerResourceSource` via a single-type-string parameter — needs the same nullable treatment or an explicit guard, confirm which at task time), and `_include`/`_revinclude` do **not** combine with system-level search in this sub-project — this mirrors the same limitation the wildcard-compartment increment already accepted for itself (roadmap: "two new `NotSupportedException` guards... a wildcard compartment search alongside `_include`/`_revinclude`"). Sort composes normally — it joins on `m.T1`/`m.Sid1` per row (`SqlBuilder.cs:364`), not on a literal type ID. `Lower.cs`'s existing null-`targetResourceType` guards (`:53-57`, `:62-68`) currently overload "null type" to mean *wildcard compartment specifically* — they must be reworked to distinguish system-level search's own null-type case from wildcard compartment's, not relaxed uniformly.

## 5. `$everything`

**Finding**: legacy's `PatientEverythingQueryGenerator.cs` composes five things, not just compartment search: (1) the Patient resource itself, `UNION` (2) compartment search (already supported), (3) a **conditional date predicate** — keep a resource if it has a matching clinical date, OR if it has no date-typed search-index row at all (legacy's own comment claims this is "Patient/RelatedPerson/Device," but the check is table-wide, not per-resource-type — a Patient with no date-typed row still survives via the same mechanism, it's simply usually true for those types, not guaranteed by type) — not an ordinary predicate, (4) an optional `_since` filter via `Transaction.VisibleDate` (an incremental-update mechanism, distinct from ordinary `_lastUpdated` search — `VisibleDate` is NULL until a transaction becomes visible, a different column and semantic from `CreateDate`), and (5) an optional **referenced-type expansion** — a separate query pulling in Practitioner/Organization/Location/Medication resources referenced *from* the compartment set, unioned in last. None of this has existing AST representation. Confirmed zero interaction with sort/paging: `$everything` has neither today, even in the legacy path (`PatientEverythingHandler.cs` explicitly disables both) — this item carries no regression risk from items 1-3 above, in either direction.

**Design, revised after review** (the original draft mapped "(1) the Patient itself" onto compartment search, which cannot produce it — compartment CTEs match rows *referencing* the patient, never the patient's own row — and proposed composing the conditional date predicate via `:missing`'s `ParamSource`-based mechanism, which requires a non-null `SearchParamId` that legacy's actual table-wide check doesn't have):

- **(1) Patient itself**: an explicit, separate union branch — a plain `ResourceSource` filtered by `_id` (or the compartment's own subject ID), not routed through `CompartmentSource` at all.
- **(2) Compartment membership**: unchanged, the existing `CompartmentSource`/`LowerCompartment` mechanism.
- **(3) Conditional date predicate**: legacy's real check (`PatientEverythingQueryGenerator.cs:202-222`) is **table-wide** — a join to `DateTimeSearchParam` filtered only by `ResourceSurrogateId`, with **no `SearchParamId` filter and no `ResourceTypeId` filter** ("does this resource have any date-typed search-index row at all, regardless of which parameter"). This is not expressible via `LowerParameterPresence`/`ParamSource` (both require a specific, non-null `SearchParamId`) — it needs one new, narrow node kind: a raw table row-existence check scoped only by `ResourceSurrogateId` (`TableExistsPredicate(TableDescriptor Table)` — no `SearchParamId`/`ResourceTypeId` fields at all; `Emit` renders it as `SELECT DISTINCT ResourceTypeId AS T1, ResourceSurrogateId AS Sid1 FROM {schema}.{table}` with no `WHERE`, mirroring `EmitCompartmentSource`'s shape minus the predicate). Compose as `Union(CompartmentSet ∩ HasMatchingDate, CompartmentSet − HasAnyDateRow)` — the *set difference* expressed as a new `Except(CteRef left, CteRef right)` primitive on `StructuralContext`, mirroring `Union`/`Intersect`'s existing one-line shape (`_ctes.Add(new CteDefinition.Except(left, right)); return new CteRef(...)`) and taking pre-built `CteRef`s directly. `StructuralContext` has no public `Except` today — only `LowerNot`'s internal, single-type-string-based one — so this is a genuinely new, small addition, not a reuse of `LowerNot`.
- **(4) `_since`**: **applies only to the compartment branch (item 2), not plan-wide.** Legacy scopes `_since` to the compartment query alone — the Patient itself (item 1) is always returned regardless of `_since`, and referenced-type expansion (item 5) is seeded from the since-filtered compartment set but is not itself re-filtered. A plan-wide `Since` field on `QueryPlan` would incorrectly drop the subject Patient from an incremental `$everything` call when the Patient itself hasn't changed — and `QueryPlan` has no existing mechanism to attach a filter to one specific CTE (confirmed: it's flat — one plan-wide `OuterPredicate`, no per-CTE equivalent). Revised mechanism: a new `VisibleSinceFilter(SqlParameterRef Since)` CTE kind (its own standalone node, not a field on `CompartmentSource` — `CompartmentSource.Predicate` is evaluated in `ReferenceSearchParam`'s own single-table scope and cannot express the cross-table `Resource`→`Transactions` join `_since` needs), rendering `SELECT DISTINCT ResourceTypeId AS T1, ResourceSurrogateId AS Sid1 FROM dbo.Resource r INNER JOIN dbo.Transactions t ON r.TransactionId = t.SurrogateIdRangeFirstValue WHERE t.VisibleDate >= @Since` (mirrors `SqlServerFhirRepository.cs`'s existing `Transactions` join syntax, e.g. lines 108/118/511/551/587 — those all select `CreateDate` today; this is `VisibleDate`, a new usage of an existing, currently-unused-here column). Compose via the **existing** `Intersect(compartmentUnion, visibleSinceCte)` primitive when `_since` is present — no new composition mechanism needed, only the one new leaf CTE kind.
- **(5) Referenced-type expansion**: a new `Union`-composed CTE, structurally similar to a `_revinclude` stage but seeded from the *filtered* compartment set (after date/`_since` filtering, matching legacy's own sequencing) rather than the match page.

Two new node kinds (`TableExistsPredicate`, item 3; `VisibleSinceFilter`, item 4) plus one new `StructuralContext` primitive (`Except`) plus new top-level composition/orchestration (items 1, 5) — not zero new AST surface as originally claimed. Exact `CteDefinition` shape for both new node kinds is a plan-time design decision informed by prototyping against `EndToEndCompilationTests.cs`'s existing style; this design fixes the *what*, task-level design fixes the *exact IR shape*.

## Testing

Each of the 5 items gets unit tests matching this compiler's established granularity (lowering-rule tests, `Emit` golden-SQL tests, end-to-end `Resolve→Lower→Emit` combined-proof tests) — no execution against a real database in this sub-project (that proof belongs to sub-project 3's differential harness, the compiler's first real live-DB test regardless of feature area). Sort-type tests read legacy's exact SQL shape as the oracle for correctness (same pattern chain/include/compartment increments used against `fhir-server`). System-level search and `$everything` tests exercise the new `Union`-based composition against hand-traced expected CTE counts/shapes, matching `PlanExplainer`/`Explain()`-based assertions established since the fourth increment specifically to catch "something silently vanishes" bugs.

## Process

Same rigor as every prior increment in this compiler's roadmap: design → Fable adversarial review of this doc → writing-plans → Fable review of the resulting plan → subagent-driven-development with per-task review → final whole-branch review.
