# cli-on-fhir (prototype)

Explore a local folder of FHIR data from the command line or from an agent over MCP (stdio). No HTTP endpoint, no database: the folder is catalogued where it is and indexed in memory with Ignixa's search indexer.

Status: alpha prototype. Design and roadmap: [`docs/features/local-cli/`](../../docs/features/local-cli/readme.md).

## Usage

```bash
# Overview of a folder: resource types and counts, patients, problems found, build cost
cli-on-fhir inspect ./my-fhir-data --fhir-version r4

# Which coding systems the data uses (SNOMED CT, LOINC, ...), with no terminology or network
cli-on-fhir systems ./my-fhir-data --top 5

# Patients, then one patient's context: root digest, one node, a code or text
cli-on-fhir patients ./my-fhir-data --sort latest
cli-on-fhir context ./my-fhir-data <patientId>
cli-on-fhir context ./my-fhir-data <patientId> --node "labs/http://loinc.org|8302-2"
cli-on-fhir find ./my-fhir-data <patientId> asthma

# Terminology from FHIR npm packages (the core package by default; add HL7 Terminology)
cli-on-fhir term load ./my-fhir-data hl7.terminology.r4@7.4.0
cli-on-fhir term lookup ./my-fhir-data http://hl7.org/fhir/administrative-gender female
cli-on-fhir term search ./my-fhir-data inpatient --terminology hl7.terminology.r4@7.4.0
cli-on-fhir inspect ./my-fhir-data --with-terminology
cli-on-fhir term lookup ./my-fhir-data http://snomed.info/sct 73211009 --tx-server https://tx.fhir.org/r4

# Check a search before running it: how each parameter resolves and how the folder populates it
cli-on-fhir search ./my-fhir-data Observation "code=http://loinc.org|8867-4&subject:Patient.gender=female" --check

# Validate resources (core definitions, loaded profiles, bindings from the terminology store), summarized by rule
cli-on-fhir validate ./my-fhir-data --type Observation --limit 500
cli-on-fhir validate ./my-fhir-data --patient <patientId> --package hl7.fhir.us.core@6.1.0
cli-on-fhir validate ./my-fhir-data --reference Patient/123 --detail

# Serve the folder to an MCP client over stdio
cli-on-fhir mcp ./my-fhir-data --terminology hl7.fhir.r4.core@4.0.1 --terminology hl7.terminology.r4@7.4.0
```

Example MCP client configuration (Claude Code, `.mcp.json`):

```json
{
  "mcpServers": {
    "fhir-folder": { "command": "cli-on-fhir", "args": ["mcp", "./my-fhir-data"] }
  }
}
```

## What it reads

- `*.json`: a single resource, or a Bundle whose `entry[].resource` items are catalogued individually.
- `*.ndjson`, `*.jsonl`: one resource per line.
- The folder is never modified. A `.ignixa/` directory inside it is skipped by the catalog but nothing writes there.

Problems (invalid JSON, objects without `resourceType`, duplicate ids, resource types unknown to the chosen FHIR version) are reported in `issues`, never dropped silently.

## Index cache

Search indexes are persisted per resource type so a new process does not pay for indexing again. The cache lives outside the data folder, in `$XDG_CACHE_HOME/cli-on-fhir` (else `~/.cache/cli-on-fhir`, or `%LOCALAPPDATA%\cli-on-fhir` on Windows), in one subdirectory per folder and FHIR version.

- `--cache-dir <path>` moves the cache root; `--no-cache` neither reads nor writes it. A cache directory inside the data folder (or a data folder inside the cache root) is refused with an `index-cache-unavailable` issue (links are resolved and case is ignored when comparing), because the folder is never written and cache files would be read as data.
- A manifest records the cache format, FHIR version, tool build, the module versions of the indexing assemblies, a hash of the search parameter definitions and every scanned file's size and last-write time. Any difference discards the whole cache and is reported as an `index-cache-rebuilt` issue with the reason and the number of changed files.
- An unreadable or inconsistent cache file is rebuilt and reported as `index-cache-corrupt`; an unwritable cache directory is reported once as `index-cache-unavailable`. Neither fails the call. These warnings describe ongoing degradation, so every response of the session carries them; the `index-cache-rebuilt` information is carried only by the first response after the rebuild. Values are persisted in Ignixa's lossless compact search value format (`Ignixa.Search.Serialization`), the same one FileSystem sidecars use.
- `inspect --build-index` reports per type whether the index came from the cache or was built, with load, build and write times.

Search parses queries with Ignixa's own search pipeline and evaluates them with Ignixa's in-memory interpreter (`Ignixa.Search.InMemory.SearchQueryInterpreter`), which matches multi-field criteria such as `system|code` within one index entry (and, for composites, one value of each component), compares the bound of a period, partial date or range that the FHIR prefix table names, and folds accents in string search. The same engine (`Ignixa.Search.InMemory.InMemorySearchEngine`, every feature enabled) evaluates:

- forward chains to any depth (`subject:Patient.name=Smith`; untyped `subject.gender=female` when only one target type defines the parameter, otherwise the call fails naming the typed forms) and reverse chains (`_has:Observation:subject:code=8867-4`), over the indexes of the types they name, built on first use;
- `_sort` on date, number, quantity, string, token and uri parameters and `_id`, several keys and `-` for descending. A resource with several values sorts by its lowest ascending and its highest descending; one with no value comes last either way; ties fall back to `_lastUpdated` (oldest first) and then id, so paging is stable. A sort key that cannot be ordered fails the call;
- `_include` and `_revinclude`, with `:iterate` and `Type:*`, for the returned page only. Included resources come back whole (not trimmed by `elements`) in `facts.included`, at most 50 (resolution stops at the cap, so `:iterate` cannot run away); they are not counted in `total` or `returned`, have their own evidence, and anything left out (the cap or the size budget) is listed in `omitted`. An include that can add nothing to the search (`Observation?_include=Patient:organization`, or a `_revinclude` whose parameter never references the searched type) is an `include-not-applicable` warning. A reference to another server, or to a resource the folder does not hold, includes and chains to nothing; references that are not local `Type/id` references (absolute URLs no Bundle entry's fullUrl names, bare ids, and canonicals under a parameter that also selects references or under `Type:*` and `*`) are not followed and are counted, per reference parameter followed, in a `references-unresolved` information issue, so an empty chain or include is not mistaken for a complete answer. A `urn:` reference is never counted there: see [Bundle references](#bundle-references).
- a `compartment` (`--compartment Patient/123` on the CLI), which limits the search to the resources in that compartment, as `Patient/123/Observation?...` does on a server, and is echoed in `facts.compartment`. Membership follows the FHIR version's CompartmentDefinition (`Ignixa.Search.InMemory.InMemoryCompartmentMembership`): an R4 Observation is in a patient's compartment when its `subject` or `performer` references that patient, a reference to another server's patient does not count, and the compartment's own resource is a member only where the definition lists `{def}` (R4 `Encounter`, R5 `Patient`). A type the definition never includes (`Organization` in a Patient compartment) matches nothing, with a `compartment-excludes-type` warning; searching the compartment's own type where the definition has no `{def}` (R4 `Patient` in a Patient compartment, where only other patients linking to it match) adds a `compartment-excludes-own-resource` information issue; a compartment resource the folder does not hold is a `compartment-resource-absent` information issue (references to it still match); a malformed value or unknown compartment type fails as `invalid-parameter`, and an STU3 `AuditEvent` or `Provenance` search in a Patient compartment, whose definition lists codes that are not search parameters, fails as `search-not-supported`.

The diagnostics of every index a search read (the searched type and any type a chain or include read) are reported in `issues`, since a resource that could not be indexed is silently absent from a chain or include otherwise. A request that cannot be answered fails with an `error` issue (exit code 1 on the CLI, `isError` over MCP) and no facts.

The 50 KB cap applies to the decoded tool-result text, i.e. the whole serialized envelope (resources, evidence, issues, omitted), not to the JSON-RPC frame, which escapes that text again and is larger. The CLI prints the same compact JSON by default; `--pretty` indents it (and so exceeds the cap).

What a search may leave unapplied is decided in one place (`Search/ParameterPolicy.cs`):

- A parameter that would change which resources match or which page is returned fails the request as `search-not-supported`: the filters `_text`, `_content`, `_query`, `_list`, `_filter` and `_not-referenced`, and any other parameter the type defines but the pipeline does not evaluate (such as `_source`); continuation tokens (`ct`, `after`; page with `offset`); `_type` unless it names exactly the searched type; a `_sort` key that cannot be ordered; and anything the parser recognises but cannot evaluate (unsupported modifiers, ambiguous chains).
- A parameter name the pipeline does not recognise, including a wrong-case one (`Family`, `_lastupdated`) or one inside a chain (`general-practitioner:Practitioner.familly`, checked against the chain's target type), fails the request as `unknown-search-parameter` with a "did you mean" hint and the type's parameter names; a chain link that can never resolve (`_has:Observation:subject:code` on Observation, which `subject` never references) fails as `invalid-search-request`; `_offset` and `_page` point at the `offset` argument. Pass `lenient` (MCP) or `--lenient` (CLI) to ignore such names with a `parameter-ignored` warning instead. **Lenient mode can widen results**: a misspelt filter is dropped and the search returns more than was asked for, so check `issues` before trusting the total.
- Only these are ignored, each with a `parameter-ignored` warning naming it, in both modes: `_format`, `_pretty`, `_contained`, `_containedType`, `_includesCount`, `_includesContinuationToken`, `_summary` values other than `count`, `_type` naming the searched type, and a parameter with no value. `param=|code` matches a code with no system.
- Date `ap` widens by 10% of the distance between the value and the current time (Ignixa's table, shared with the SQL backend), so an `ap` result can change as time passes; other prefixes do not depend on the clock.

Indexer failures are reported as `index-extraction-failed` from the event's structured fields only: the search parameter, expression, element type and converter (from the definitions), the resource by its tool-wide name, the exception type, and digests of a value and of the exception's message, never the indexer's text, which quotes folder data. The console log on stderr (CLI and MCP server) receives the same redacted text.

`_lastUpdated` is indexed (by `Ignixa.Search.InMemory.LastUpdatedSearchIndexer`) from `meta.lastUpdated` only when it is a FHIR instant (date, time and timezone); anything else is reported as an `index-extraction-failed` issue and the resource does not match `_lastUpdated`.

The folder index is Ignixa's own (`SearchIndexerFactory`) plus the in-memory `_lastUpdated` entry, so it holds what the server's index holds: ContactPoint is indexed as its value with no system, as the search page's token mapping specifies (`telecom=555-1234`; `telecom=phone|555-1234` does not match, use the `phone` or `email` parameter); a Quantity whose `unit` differs from its `code` is also indexed under the unit (`value-quantity=185||lbs`); a `urn:` reference that names no Bundle entry is kept as an untyped reference (see [Bundle references](#bundle-references)), so `subject=urn:uuid:...` matches it; a `canonical` under a reference parameter (R5 `_profile` over `meta.profile`, `instantiates-canonical`) is added in memory only (`CanonicalReferenceSearchIndexer`; the server stores nothing for it until #430) and matched as a canonical: `url` matches every version, `url|1.0` only that one; a chain, `_has` or include through a parameter that selects only canonicals fails as `search-not-supported` whatever the data, while one through a parameter that also selects references (R5 `RequestOrchestration-participant`) follows the references and counts the canonicals in `references-unresolved`; and a Range indexes as a number or quantity range (R4 `probability`).

## Search plans

`plan_fhir_search` (`search --check`) reports how a query would run without running it. It goes through the same parse and bind path as `search_fhir_resources` (digest ids, the parameter policy, chain diagnosis, the compartment) and is then compiled by the same in-memory engine over no resources, so every refusal (`unknown-search-parameter` with a suggestion, `search-not-supported` including the canonical-only chain and include refusal, `digest-not-supported`, `invalid-search-request`) is the one the search gives, with the same issues, and a query the plan accepts is one the search accepts.

- **Per parameter** (in query order, then sort keys and includes): the outcome (`compiled`, `known-miss` with the parser's reason, `ignored` in lenient mode), the modifiers and, for number, date and quantity parameters, the comparison prefixes applied, and each search parameter definition it resolved to (`resolves`: role `filter`, `chain`, `reverse-chain`, `sort`, `include` or `revinclude`; the type it is evaluated on; code, url, type and FHIRPath expression; for a chain or include the target types). A chain lists every link in order, so `subject:Patient.name` resolves `Observation.subject` (targets `Patient`) then `Patient.name`.
- **Population:** each definition says how many resources of its type in the folder's index have at least one entry for it (`populated` of `indexed`; every resource for `_id`), reading the index of each type the plan names. A compiled parameter that cannot match anything here is a `parameter-unpopulated` warning: a link no resource populates, or a token filter whose values have text only (use `:text`). `:missing=true` and `:not`, which match an absent value, raise no such warning.
- **Top values:** a token filter lists its ten most common values as `system|code` (`|code` with no system, `system|` for a system with no code, which `param=system|` matches) with resource counts, most first, from the index entries; systems and codes come from the data, so one not shaped as such is a digest (an `invalid-value` note), and displays are never shown.
- **Size:** the response stays under the 50 KB cap: when the plan does not fit, top values are cut to three per definition, then dropped, then parameters from the end, then issues, each cut listed in `omitted` (`size-budget`). `execute` (`--execute` with `--check`) also runs the search and returns its facts in `facts.results` with its evidence, `omitted` and `next`; the plan is fitted to half the cap and the search is told to leave the plan's size unused, so the page is sized for the combined response.
- **Paging:** the plan checks `count` and `offset` as the search does (`count` 0 fails, more than 50 is a `count-clamped` warning), and without `execute` its `next` is the search with the same arguments, paging included.

## Bundle references

Transaction and collection Bundles reference their own entries by `fullUrl`, usually `urn:uuid:...`. The catalog records every entry's `fullUrl`, and before a resource is indexed each `reference` naming a catalogued entry (a `urn:uuid:`/`urn:oid:` or an absolute URL, `_history` ignored) is rewritten to the entry's relative `Type/id`, in the tool's own parse only; the file is never changed. So `Encounter?subject=Patient/<id>`, `subject.gender=female`, `_include=Encounter:subject`, `_has` and compartments work across a Bundle, including parameters whose expression resolves the reference (R4 `Observation?patient=`, `subject.where(resolve() is Patient)`), which index nothing for a `urn:`. This is the reference the server stores after processing the Bundle as a transaction.

- A reference is looked up in its own Bundle first. In an entry whose fullUrl is RESTful (`http://a.example.org/fhir/Encounter/e1`), a relative reference (`Patient/123`) is first made absolute against that base, as R4 bundle.html §2.36.4.1 requires, and stays relative when no entry has that URL; an entry with no `id` takes the id of its RESTful fullUrl (`Patient/123`, when the type matches), otherwise a synthetic one.
- Beyond the spec, a reference its own Bundle does not name is then looked up across the folder's fullUrls, so an NDJSON resource (or another Bundle) can name an entry. This relies on `urn:uuid`s and absolute URLs being unique across the folder; every such resolution is counted in one `bundle-reference-resolved-cross-scope` information issue per type index (naming up to five as `resource -> reference = Type/id`). A fullUrl that names two different resources in a scope (two Bundles reusing one `urn:uuid` for different patients, seen from an NDJSON file) resolves nothing there.
- Returned and included resources keep their JSON as written, so they still show `urn:uuid:...`. `facts.resolvedReferences` maps, per returned resource, each Bundle reference it shows to the `Type/id` it was matched as (`{"Observation/o1": {"urn:uuid:aaaa-1": "Patient/pa"}}`); it is keyed by resource because one fullUrl can name different resources in different Bundles, lists at most 100 references (the rest are counted in `omitted`), leaves out references an `elements` projection removed, and is absent when there are none.
- A `urn:` reference that names no entry stays as written and is counted, distinct per resource, in one `unresolved-bundle-reference` information issue per type index (located at the first, naming up to five), which every search reading that index carries. `references-unresolved` skips exactly those, so each is reported once; it still counts canonicals, absolute URLs, bare ids and a `urn:` in a `uri` element (R4 `ConceptMap.sourceUri` under `source-uri`), which is not a Bundle reference.
- An absolute reference no fullUrl names is a reference to another server, as before.
- Resolution depends on every Bundle in the folder; the cache manifest lists every file, so editing any of them rebuilds every cached index.

`freshness.staleFiles` is recounted by listing the folder and comparing each file's size and last-write time with what the catalog recorded (the count is reused for 2 seconds so back-to-back tools share one walk). If the folder can no longer be listed the value is null and a `freshness-unavailable` warning says why.

A type that a search, a read or a patient tool reads carries a `duplicate-id` warning when the catalog dropped resources of that type for repeating an earlier type and id (count, and up to five as `Type/id used from <file>, ignored in <file>`): the answer comes from the first occurrence only. An id-less Bundle entry whose RESTful fullUrl gives it the id of a resource in a later file shadows that resource this way.

Every response uses the shared envelope: `facts`, `derived` (always null), `evidence`, `omitted`, `absent`, `issues`, `freshness` (`indexBuiltAt`, `staleFiles`) and `next`. All of them are always present, as `null` where there is no value (for example `facts` of a failed call or `indexBuiltAt` when the folder cannot be read); `next` is a list of suggested calls `{ "tool", "args" }` (the MCP tool name; the CLI verb of that tool takes the same arguments), empty when there is none. `next` is built from the response's structure only (node keys, ids, offsets, type names), never from resource content.

## Patient tools

A patient's context is the Patient resource plus every resource in its Patient compartment by the FHIR version's CompartmentDefinition (the same membership as `--compartment`). The Patient is added explicitly, because the R4 definition has no `{def}` and so does not make it a member of its own compartment; under R5 it is counted once. Types whose membership cannot be evaluated (STU3 `AuditEvent`, `Provenance`) are left out with a `compartment-type-unevaluable` warning naming them. Membership comes from the compartment; every value, rule and date from FHIRPath (`Ignixa.FhirPath.Evaluation`) over the resources with their Bundle references resolved (`Patients/ClinicalRules.cs` holds every expression). The answers are deterministic for a folder, an index and an `asOf`.

- `patient_list` (`patients`): per Patient, `name` (the first `official`, else `usual`, else use-less name, as its given names then family; never its free `text`), `id` (its digest when it is not a FHIR id), `gender`, `birthDate`, `resourceCount` (the context's size), `earliestDate`/`latestDate` (each resource's main date, see below, as written; no time window) and the `domains` present (demographics, problems, medications, allergies, encounters, labs, procedures, immunizations, documents). Sorted by `name` (case-insensitively, unnamed last, then id) or `latest` (newest first, undated last, then id), paged (`count` 10, at most 50, `offset`). Evidence is the page's Patient resources.
- `context_get_root` (`context`): demographics and one stub per domain (`nodeKey`, `count`, at most five `items`, the `rule` as applied, `excluded` = resources of the domain's types the rule left out, `window` for time-dependent domains), and `otherTypes` counting compartment resources no stub covers. `next` lists `context_expand` for each non-empty domain and `search_fhir_resources` with the compartment for each other type. It cites as evidence every resource whose values it shows. On the samples it measures about 9 KB, over the 5 KB the design aims at (15 cited items with UUID ids and long file names).
- `context_expand` (`context --node`): `problems`, `medications`, `allergies`, `encounters`, `labs` (lab codes, no resources), `problem/Condition-<id>` (the condition, then each MedicationRequest or MedicationStatement whose `reasonReference` references it or whose `reasonCode` shares a system and code with its code, with `linkedBy`), `encounter/Encounter-<id>` (the encounter, then every resource in its Encounter compartment) and `labs/<system>|<code>` (the series, newest first). Items come with their resources as written, trimmed by `elements`, within the 50 KB budget, with `facts.resolvedReferences` as search gives it; `omitted` and `next` give the next `offset`. A malformed key is `invalid-node-key`, a key naming nothing in this patient's context `unknown-node-key`, both request errors.
- `context_find` (`find`): `system|code` matches that code in each resource's main code; `|code` a code without a system; a bare token codes in any system first, then texts; a query with whitespace texts only (case-insensitive substring of the main code's `text` or a coding `display`). Code matches come first, each group in compartment order, with `matchedBy`, the distinct `nodeKeys`, and the page's resources. Nothing found is an `absent` entry naming what was searched.

Rules (R4; stated in `facts` as applied):

| Domain | Membership and order |
|--------|----------------------|
| problems | `clinicalStatus.coding.where(system = 'http://terminology.hl7.org/CodeSystem/condition-clinical' and (code = 'active' or code = 'recurrence' or code = 'relapse')).exists() and verificationStatus.coding.where(system = 'http://terminology.hl7.org/CodeSystem/condition-ver-status' and (code = 'refuted' or code = 'entered-in-error')).empty()`; active first |
| medications | `status = 'active' and (doNotPerform.empty() or doNotPerform = false)`; MedicationRequests and MedicationStatements together, active first. The display is the `medicationCodeableConcept`'s first coding display, else the referenced Medication's `code` (contained or `Medication/id`; the Medication is cited, or `absent` when the folder lacks it) |
| allergies | every AllergyIntolerance, any status. None is an `absent` entry with the compartment, the parameters that put AllergyIntolerance in it and the folder's count: no record is not "no known allergies" |
| encounters | `period.start` at or before `asOf` and `status != 'planned' and status != 'cancelled' and status != 'entered-in-error'` |
| labs | Observations whose main date is at or before `asOf`, `status != 'cancelled' and status != 'entered-in-error'`, and `category.empty() or category.coding.where(system = 'http://terminology.hl7.org/CodeSystem/observation-category' and (code = 'laboratory' or code = 'vital-signs')).exists()`; one series per `code.coding.where(system.exists() and code.exists()).first()`; most observations first, then key. Latest = the newest; trend = newest against oldest of the last three values when all are numeric `valueQuantity` in one unit (`unit`, else `code`) without a `comparator`, `flat` within 5% of the oldest, otherwise `n/a` |

Order: every list is newest first by the date its items show (the main date below), compared by that date's earliest instant (a date or a year counts from its first moment; a time without an offset is read as UTC), undated items last, then by id. The `asOf` window uses the same date: an item is in it when that earliest instant is at or before `asOf`. `patient_list` reads `earliestDate`/`latestDate` on the same basis.

Main clinical date (first expression yielding a date; types not listed have none): Condition and AllergyIntolerance `onset.ofType(dateTime)`, `onset.ofType(Period).start`, `recordedDate`; Observation `effective.ofType(dateTime)`, `effective.ofType(Period).start`, `effective.ofType(instant)`, `issued`; DiagnosticReport the same without `instant`; Encounter `period.start`; MedicationRequest `authoredOn`; MedicationStatement `effective` (dateTime, Period start), `dateAsserted`; MedicationAdministration `effective`; MedicationDispense `whenHandedOver`, `whenPrepared`; Procedure `performed` (dateTime, Period start); Immunization `occurrence.ofType(dateTime)`, `recorded`; DocumentReference `context.period.start`, `date`; Composition `date`; CarePlan `period.start`, `created`; ImagingStudy `started`; ServiceRequest `occurrence` (dateTime, Period start), `authoredOn`. `patient_list` returns this table in `facts.dateRule` for the types the folder holds. Main codes (what `context_find` matches and items display): `code` for Condition, Observation, AllergyIntolerance, Procedure, DiagnosticReport and ServiceRequest; Encounter `type`; the medication's CodeableConcept; Immunization `vaccineCode`; DocumentReference and Composition `type`; CarePlan `category`; ImagingStudy `procedureCode`.

Time: encounters and labs are read as of `asOf`, the session clock's current instant truncated to the second (`FolderSession` takes a `TimeProvider`), stated in `facts.asOf` and in each `window` (`from` null, `to` = `asOf`). R4B shares R4's rules (the elements and codes they read are the same). Under STU3 or R5 they were not checked: a `domain-rule-unsupported-version` warning says so, the status and category rules are not applied (every Condition, medication and Observation is listed), and dates and codes are read by the R4 element paths.

Untrusted content: items, node keys, `next` and `absent` never carry narrative (`text.div`), notes, attachments, string values, a CodeableConcept's `text` or a HumanName's `text`; those stay inside the returned resources. Items do carry coded data (`system|code`, a coding's `display`, a quantity's `unit`) and demographics the name's given and family parts, all copied as written: that is folder data, not instructions. Values bound to a code or a date are shape-checked before they are copied: a status as a FHIR `code` (words of non-whitespace, non-control characters separated by single spaces, at most 64 characters), a gender as one of `male`, `female`, `other`, `unknown`, a comparator as `<`, `<=`, `>=`, `>` (and `ad` in R5), a birth date as a FHIR `date`; a value that fails is shown as its digest and reported once per type as an `invalid-value` warning that does not echo it. Once a terminology call has loaded the store in the session (the patient tools never load it, so they never download a package, and never ask `--tx-server`), a status (`clinicalStatus` for Condition and AllergyIntolerance), gender or comparator that passes the shape check is also checked against its element's required-binding ValueSet: one outside it is shown as its digest with an `invalid-value` warning naming the element and the ValueSet, never the value; one the loaded terminology cannot decide is shown as written with a `binding-not-checked` note. `facts.valueBindings` says `checked` or `not-checked` (no terminology loaded: only the shape was checked). In node keys a code system is kept only when it is shaped as an `http(s)` URL, a `urn:oid:` or a `urn:uuid:`, a code only when it is a plain token (letters, digits and `-._:/#%+`, at most 64 characters); anything else is replaced by its digest.

Ids: every tool names a resource whose id is not a FHIR id (1 to 64 letters, digits, `-` or `.`) by its digest, `Type/~` and 16 hex digits of the id's SHA-256: in evidence, `resolvedReferences`, item references, node keys, `next`, `absent` and every issue or message that names a resource (duplicate ids, stale or unreadable resources, extraction failures). `get`/`read_resources` (each resource once, whichever names it is asked for by), search's `_id` (with any modifier, percent-encoded or in a comma list) and `compartment`, and the patient tools' `patientId` accept the digest; a digest that names nothing is a real `absent` (or matches nothing). A digest anywhere else in a query (a reference value, a chain's `_id`) cannot be resolved and fails the request as `digest-not-supported`. The resource's JSON is returned as written. `inspect` lists an `invalid-id` warning per such resource, and every response that shows one carries an `invalid-id` warning for its type, located at the first. A resource without an id is named by the catalog (by its Bundle entry's RESTful fullUrl id, else `synthetic-` and a hash of its file and position), and a response that shows one carries a `synthetic-id` information note. A reference as written appears in messages and `resolvedReferences` only when it is a `urn:` or http(s) reference with no whitespace, control character, quote, angle bracket, backslash or `|`; otherwise by its digest.

## Terminology

The terminology tools answer from a store of `CodeSystem`, `ValueSet` and `ConceptMap` resources, built on the first terminology call (`folder_inspect` never triggers it unless `withTerminology` / `--with-terminology` is given) and shared by every later call of the session.

- **Sources:** the folder's own terminology resources, then FHIR npm packages: `--terminology <id@version>` (repeatable) on `mcp`, `inspect` and the `term` verbs, else the FHIR version's core package (`hl7.fhir.r3.core@3.0.2`, `hl7.fhir.r4.core@4.0.1`, `hl7.fhir.r4b.core@4.3.0`, `hl7.fhir.r5.core@5.0.0`) as the *default*, then each `terminology_load_package` / `term load`. When the session's first terminology call is itself a load of the default core package, that call loads it (explicitly) instead of the default load.
- **Which version answers** a url asked for without a version:
  1. the folder's;
  2. otherwise by package authority: for a `http://terminology.hl7.org/` canonical, an `hl7.terminology.*` package outranks every other package; core (`hl7.fhir.*.core`, whether loaded by default or explicitly) ranks below every other package for every canonical;
  3. among the candidates of the first-loaded package of that rank, the highest version when every candidate is strict SemVer, or when they all declare the same R5 `versionAlgorithm` (`semver`, `integer`, `date`, `alpha`). Versions are never compared across package ids: core stamps its copies of THO systems with its own FHIR version (`4.0.1`), which would otherwise outrank THO's own SemVer (`2.0.0`);
  4. otherwise load order.

  Whenever there were several candidates, the answer carries an `other-versions-loaded` information issue naming each version and source; pass a version to choose another.
- **Conflicts:** two sources defining one `url|version` with the same content count once; with different content the one of higher precedence (the same authority ranks, then load order) answers and every answer that uses it carries a `canonical-conflict` warning naming both sources and files (`terminology_list` lists the first five of all of them).
- **Where packages come from:** the tool's package store `<cache root>/packages` (`--cache-dir`, else the user cache directory; never inside the data folder, by the index cache's overlap check, so a store there is refused with a `package-store-unwritable` warning), then the standard FHIR package cache `~/.fhir/packages/<id>#<version>` (`--fhir-package-cache` to point elsewhere; read only), then a download from the FHIR package registry `https://packages.fhir.org/` and nowhere else: the package document `/<id>` (for `dist-tags.latest` when a bare id is given, and each version's SHA-1 `shasum`) and the archive `/<id>/<version>`. Redirects are not followed, responses are size-capped (8 MB document, 64 MB archive) and time-bounded, and the archive must match the published SHA-1, which guards against corruption (authenticity rests on TLS to packages.fhir.org). A downloaded archive is read and checked (its `package.json` must name the requested id and version) before it is stored as `<id>#<version>.tgz` with a sidecar recording its SHA-512, re-checked on every later read; a mismatch is a `package-store-corrupt` error, never read past. `--offline` disables the network: packages then load only from the store or the FHIR package cache, and a bare id fails with the versions held locally. Only FHIR npm packages are downloaded, only for a package someone asked for or the default core package; SNOMED CT, LOINC and other licensed content are never downloaded.
- **Package reading:** in memory, never extracted to disk. Only regular JSON files directly under `package/` are read (not `.index.json`, not `package/example/`); entries outside `package/` (the core packages ship `other/` and `openapi/`), in subfolders, or that are not regular files are counted in `files.filesIgnored`. Limits: 64 MB compressed, 512 MB expanded, 20,000 entries, 32 MB per file; a repeated path, a missing `package/package.json` or anything over a limit fails the package (`package-invalid`). `Ignixa.PackageManagement`'s `NpmPackageAcquirer` is not used: packages.fhir.org serves the archive at `/<id>/<version>` instead of npm version metadata and publishes no SHA-512 `integrity`, and its strict extractor rejects the core packages' entries outside `package/`.
- **Model:** concepts with display, definition, designations, properties and status; `inactive` when the status property (declared with `http://hl7.org/fhir/concept-properties#status`, or named `status`) is `retired` or `inactive`, or the `inactive` property is true (`deprecated` is still active). The hierarchy comes from nested `concept.concept`, the `parent`/`subsumedBy` and `child` properties (by name or by their `concept-properties` URI); references to undefined codes and cyclic edges are left out and reported as `hierarchy-defects`. Every concept's ancestor set is computed at load. A CodeSystem with `content = not-present` (how the core packages declare SNOMED CT, LOINC, RxNorm, ...) or a supplement provides no concepts: its system counts as not loaded.
- **Case:** a CodeSystem with `caseSensitive: false` matches codes in any case; one that does not state `caseSensitive` also matches them (R4: accept codes in any case) with a `case-insensitive-match` note naming the code's own spelling; `caseSensitive: true` matches exactly. ValueSet membership (`terminology_validate_code` with `valueSet`) follows the code's system the same way.
- **Abstract concepts:** expansion codes carry `abstract: true` for concepts whose `notSelectable` property is true (groupers not meant for use in data).
- **Not found** distinguishes `system-not-loaded` (including such a stub, which is cited as evidence), `version-not-loaded` (with the loaded versions), `code-not-in-version` (the loaded version is complete) and `code-not-in-loaded-content` (fragment or example content: absence is not authoritative). `terminology_subsumes` answers `not-subsumed` only when both codes are in a complete CodeSystem; incomplete content gives `unknown`. `terminology_validate_code` answers `invalid` only when complete content decides it, otherwise `unknown` with the reason; a right code with a display that matches neither its display nor a designation is `invalid` with reason `display-mismatch` and the expected display in `facts.display`, as R4 `$validate-code` and tx.fhir.org answer it (locally and remotely alike). A CodeSystem whose `hierarchyMeaning` is not `is-a` (`grouped-by`, `part-of`, ...) answers `unknown` for the subsumption of two distinct codes.
- **ValueSet expansion** evaluates compose include/exclude with listed concepts, whole systems, nested ValueSets (intersected; each nested ValueSet is expanded once per request however many includes reach it, and include cycles are found before expanding: no include inside a cycle is followed, so every member of the cycle is reported incomplete with a `value-set-cycle` warning, the same whichever member is asked for) and the filters `is-a`, `descendent-of`, `is-not-a`, `generalizes`, `child-of` (on `concept`) and `=`, `in`, `exists` (on a property). Anything else (other filters such as `regex`, a system that is not loaded, content that is not complete) makes the expansion incomplete: `facts.complete` is false, with an `expansion-incomplete` warning and one issue per rule. Codes a ValueSet lists for a system that is not loaded are included as listed, with a `codes-not-checked` note. Expansions above 100,000 codes fail as `expansion-too-large`.
- **ConceptMaps** (R4 `equivalence`, R5 `relationship`; `mapped` only for a target that is not `unmatched`, `disjoint` or `not-related-to`) translate a source system and code to targets, through one named map or every map with a group from the system; a group's `unmapped` `provided`/`fixed` rule applies to codes it does not list, `other-map` is reported, not followed; `dependsOn`/`product` targets are flagged `conditional`, not evaluated; reverse translation is not supported.
- **`folder_inspect` terminology section:** once the store is loaded, per code system used in the folder, the distinct codes and how many resolve, are inactive or unknown, from every type's token search-index entries (leaving out parameters over Identifier elements); otherwise `facts.terminology.status` is `not loaded`.
- **Untrusted content:** displays, definitions, designations, comments and property values are terminology content copied from the package or folder into `facts`: data, not instructions. `next` is built from the caller's own arguments and paging only; issue messages, `absent` and evidence name things by `system|code`, canonical `url|version`, package `id@version` and file path, each replaced by its digest when it is not shaped like what it names (a "code" holding a sentence). Evidence for a package resource is `<id>#<version>/package/<file>`, the path it has in a FHIR package cache; a package as a whole (`terminology_list`, `terminology_load_package`) is cited as `id@version` with its `package/package.json`.
- **Remote terminology server (opt-in):** `--tx-server <base url>` (for example `https://tx.fhir.org/r4`; absolute https, http only on this machine, no credentials; not with `--offline`) on `mcp`, `inspect` and the `term` verbs. It is asked only when the store cannot answer: `lookup`, `subsumes` and `validate_code` against a system (or version) that is not loaded (including content not-present stubs such as SNOMED CT or LOINC in core), `validate_code` and `expand` against a ValueSet that is not loaded or whose local expansion is incomplete, `translate` when no loaded ConceptMap applies. A code missing from a loaded system is answered locally and never sent. Requests are GETs of the standard operations (`CodeSystem/$lookup`, `$validate-code`, `$subsumes`, `ValueSet/$expand` with `count`/`offset`/`filter`, `ValueSet/$validate-code`, `ConceptMap/$translate`) with `Accept: application/fhir+json` whose query carries only `system`, `code`, `version`, `display`, `url`, `filter`, `count`, `offset`, `codeA`/`codeB` and the target system, never resource content. Answers have `facts.source.kind` = `tx-server` with the server and the version it reported, and a `tx-server-answered` note. Responses are bounded (10 s, 2 MB) and untrusted: displays go into facts as data, messages and OperationOutcome text are not used, redirects and urls in responses are not followed. A timeout or network failure fails the call as `tx-server-unavailable`; an HTTP error, an OperationOutcome (its issue codes are named) or a response of the wrong shape as `tx-server-error`; neither becomes `system-not-loaded`, `not-subsumed` or `invalid`. The one exception is an HTTP 404 whose OperationOutcome has the issue code `not-found` on `$lookup` and `$validate-code`: the server does not know the code, reported as outcome (or reason) `not-found-by-tx-server` with `source` tx-server, an `absent` entry naming the server and a `not-found-by-tx-server` warning; it is never the local `code-not-in-version`. `$translate` parameter names follow the server's FHIR version, read once from its CapabilityStatement (`metadata`, no parameters): R4 `code`/`targetsystem`, R5 `sourceCode`/`targetSystem`, both when it does not say (with a `tx-server-version-unknown` note). Successful answers are cached in memory for the session (no disk cache). `terminology_search`, `terminology_navigate` and `terminology_list` stay local.
- **Validation adapter:** `validate_resources` checks bindings through `Terminology/StoreTerminologyService.cs`, an `ITerminologyService` over this store (and `--tx-server`), described under [Validation](#validation).
- **Not done:** native SNOMED CT RF2, LOINC or RxNorm loaders; `:below`/`:above`/`:in` search modifiers through the store.

## Coding systems

`folder_code_systems` (`systems`) answers "which coding systems does this dataset use?" without loading terminology or touching the network.

- **What is counted** (`facts.basis`): every Coding in the catalogued resources' JSON (an object with a string `code` and a string `system`, or any object with a string `code` in a `coding` array), extensions and contained resources included, and every Quantity with a unit system (UCUM). The walk reads each file once per session (about 0.7 s for the 10,153-resource NDJSON sample) and uses no search index. It does not use the index because Ignixa's indexer gives FHIR `code` elements the system their binding implies (from `Ignixa.Search.Generated.*CodeSystemMappings`), so an index-based inventory would report systems the data never wrote.
- **Implicit codes:** values of FHIR `code` elements that resources and their backbone elements declare with a FHIR-defined binding (`Patient.gender`, `Observation.status`, `Patient.contact.gender`, ...; the element list comes from the FHIR version's schema, `CodeSystems/ImplicitCodeElements.cs`) carry no system in the data. They are listed separately under `implicitCodes` by element, not counted under `systems`. Each gives the `system` its binding implies, the one the indexer files it under (`Patient.gender`: `http://hl7.org/fhir/administrative-gender`), or `null` where the binding implies no single code system (R4 `Task.intent`, whose ValueSet draws on two). Code elements of datatypes (`HumanName.use`, `ContactPoint.system`, `Address.use`, `Identifier.use`, `Quantity.comparator`, `Narrative.status`, ...) and of elements repeating another element's definition (`Questionnaire.item.item`) are not counted; `facts.basis` says so.
- **Per system:** the URI as written (or its digest when it is not an http(s) or urn URI without whitespace or control characters, with an `invalid-value` note), a well-known name and steward (`CodeSystems/WellKnownSystems.cs`, from FHIR R4 terminologies-systems.html and the THO NamingSystems), the kind (`external`, `hl7-v2`, `hl7-v3`, `hl7-terminology`, `fhir`, `unknown`), distinct codes, codings, resources, codings per element (`Observation.code` versus `Observation.component.code`, at most 10) and the most frequent codes as `system|code` with counts (`top`, default 5, maximum 50). No display from the data is ever shown. Paged by usage (`count` 10, at most 50, `offset`), ties by URI.
- **Hints** (information issues and per-system flags): `non-preferred-uri` (an OID form or alias of a well-known system, naming the preferred URI), `not-a-fhir-canonical` / `possibly-not-a-fhir-canonical` (a `http://hl7.org/fhir/CodeSystem/<name>` or `.../ValueSet/<name>` URI used as a system that the loaded terminology does not define: checked against loaded terminology when there is some, by pattern only otherwise, `facts.fhirCanonicalCheck` says which; `suggestedCanonical` is only ever a canonical known to exist, one the loaded terminology defines, or with none loaded a well-known system), `codings-without-system` (per element), and `tx-server-not-enabled` when SNOMED CT, LOINC or RxNorm appear and no `--tx-server` is set.
- **Terminology:** only when it is already loaded in the session (or `withTerminology`; on the CLI `--with-terminology` or any `--terminology`), each system says `loaded` (`local` with package, content and version, `not-loaded`, or `tx-server-available`) and how many distinct codes resolve, are inactive or are unknown. `next` suggests `terminology_load_package` for the HL7 Terminology or core package when systems they carry are not loaded.
- `folder_inspect` always carries `facts.codeSystems` (the ten most used systems with name, distinct codes and codings, from the same walk) and a `next` call to `folder_code_systems`.

## Validation

`validate_resources` (`validate`) validates resources with `Ignixa.Validation` (as `tools/Ignixa.Validation.Cli` does) and summarizes the result for an agent.

- **Scope:** the folder (no scope arguments, catalog order); `resourceType` / `--type`, narrowed by a search `query` / `--query` (search syntax, parsed and evaluated exactly as `search` does, so the same issue codes apply) and by `patient` / `--patient` (that patient's compartment); `patient` alone (the Patient, then its compartment's members); or `references` / `--reference` (exact `Type/id`s, not combined with the others). At most `limit` resources per call (default 200, maximum 2000; with `detail` 10 and 50; more is clamped with a `limit-clamped` warning), from `offset` in scope order; the rest is in `omitted`, and `next` repeats the call at the next offset.
- **Against:** the core StructureDefinition of each resource's type, and each `meta.profile` whose StructureDefinition is loaded: from the folder, or from `packages` / `--package` (`id@version`, acquired like `terminology_load_package`, from the package store, the FHIR package cache or packages.fhir.org unless `--offline`, which also loads their terminology). A claimed profile that is not loaded (or cannot be built into checks) is a `profile-not-loaded` warning naming the url; `profile` / `--profile` validates against one profile (and the core definition) instead, restricting the scope to its type, and fails as `profile-not-loaded` when it is not loaded. Each schema runs on its own, so every issue names the StructureDefinition that raised it; an issue a profile repeats from the core definition counts once, under the core definition.
- **Bindings:** required and extensible bindings are checked against the session's terminology store (the folder's terminology, the configured packages, else the core package) and, with `--tx-server`, that server for a ValueSet or system not loaded locally (codes only; one request per ValueSet, system and code per session). A ValueSet or system that is not loaded, an incomplete expansion, an ambiguous system, a failing server or a server answering `result: false` because it lacks the system (`x-caused-by-unknown-system`, a not-found issue) mean the binding was **not checked** (`binding-not-checked`), never that it passed or failed; a failed remote question is not cached. Preferred and example bindings carry no conformance requirement and are not checked; displays are not checked (`facts.against.displaysChecked` is false).
- **Depth:** `full` (default) runs structure, cardinality, types, required and extensible bindings, invariants and slicing; `spec` runs structure, cardinality, types and required bindings only. `facts.against.checksNotRun` lists what did not run: at `spec` invariants, slicing, extensible bindings and complex choice variants, and since every resource is subject to invariants (`ele-1`, `dom-*`) no resource is `valid` at `spec` (each carries a `depth-spec` note); at every depth extensions and displays.
- **Verdicts:** `valid` only when every check that applies ran and none failed; `invalid` on any error; `unknown` when no check failed but one could not be evaluated or did not run (a required binding not checked, a profile not loaded, a FHIRPath constraint the engine cannot evaluate, a deferred slicing, the nesting limit, `depth-spec`, `extensions-not-validated`); `unreadable` when the resource could not be read (at most 20 listed as issues, the rest counted in `omitted`). `facts.notChecked` counts the unconcluded checks by rule (and unchecked extensible bindings, which cannot change a verdict).
- **Validator gaps the tool detects itself** (`Validation/ValidatorGapDetectors.cs`, one detector per gap in `src/Core/Ignixa.Validation`, to delete when the validator closes it): a text-only CodeableConcept under a required binding, which the validator passes unchecked, is `binding-not-checked`; any extension, which the validator never validates, is `extensions-not-validated`. Either makes the verdict `unknown`.
- **Summary:** `facts.groups` groups the issues by severity, profile, rule (the validator's issue code, `invariant` with the key in `constraint`, or the unconcluded-check name), constraint, ValueSet (for binding rules) and element path without repetition indexes, with issue and resource counts, up to three sample resources (the evidence) and the tool's own `description` of the rule (`Validation/RuleDescriptions.cs`; none for a rule it does not know); errors first, then by count; at most 50 groups, the rest counted in `omitted`, all within the 50 KB cap (then issues and `absent` are trimmed, also counted).
- **Untrusted content:** validator messages quote the data (values, property names) and profile content (constraint `human` text, patterns), so no summary shows them: only codes, constraint keys and canonicals, each replaced by its digest when not shaped as one, and paths whose segments not shaped as element names, and every unknown property's name, are digests. `next` is built from the call's own arguments, offsets and sample references. `detail` / `--detail` adds each resource's full OperationOutcome in `facts.outcomes`, labelled `outcomesContent: resource-content`: its texts are data, not instructions.
